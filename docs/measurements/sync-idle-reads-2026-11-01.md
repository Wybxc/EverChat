# 空闲同步 SQL 读取实验

日期：2026-11-01。本文保留修复前基线；业务修复及本地验证见[后续记录](sync-idle-reads-after-2026-11-01.md)。生产离线升级与发布尚未执行。

结论：Library 的完整列表轮询是本次额度耗尽的主要嫌疑路径，生产聚合与本地复现相互支持。另确认 Conversation 恢复任务的查询在冷启动时扫描全部历史任务。修复应先消除空闲全量轮询，再消除冷启动扫描，并保留鉴权与断线恢复。

## 生产证据

[脱敏聚合报告](sync-idle-production-2026-11-01.json)来自此前只读 Cloudflare GraphQL 查询。额度周期为 `2026-10-31T00:00:00Z` 至 `2026-11-01T00:00:00Z`，即北京时间 10 月 31 日 08:00 至 11 月 1 日 08:00。

| 对象类型     | SQL 读取行数 | SQL 写入行数 |
| ------------ | -----------: | -----------: |
| Library      |    4,264,432 |        2,056 |
| Conversation |      861,036 |       27,506 |
| UsageStore   |        2,137 |        1,209 |
| ShareStore   |           40 |            4 |
| 合计         |    5,127,645 |       30,775 |

Library 占约 83% 的读取。北京时间 02:00～03:00，该对象读取 436,400 行、写入 0 行，记录到 372 次成功 jsrpc、0 次 Alarm；多段五分钟窗口均为约 36,392 行、31 次 jsrpc。03:40～03:45 开始出现集中异常，之后成功读取为零。

这说明该空闲窗口的主要读取并非维护 Alarm。源码中的十秒全量列表轮询与这种稳定请求模式一致，但聚合数据不提供具体方法和设备，不能断言来自哪一台电脑或手机，也不能将全部 jsrpc 都认定为列表查询。

上述数据来自自适应分析，可能与精确计费计数不同。不能把超过 500 万的差额理解为额外免费额度。官方 Free 额度为每日 500 万读取行、00:00 UTC 重置；KV 读取也计入 SQLite 用量。[Cloudflare 定价说明](https://developers.cloudflare.com/durable-objects/platform/pricing/)

## 复现方法

```sh
pnpm measure sync-reads --output /tmp/everchat-sync-reads.json
```

最终成功报告：[本地原生计数](sync-idle-reads-native-2026-11-01.json)，`complete: true`。命令成功退出，报告只在本地运行时关闭后发布；RPC 返回值在关闭前转为普通 JSON，避免保留失效的运行时代理。中途失败的运行不作为验收报告。

夹具位于 `scripts/measurements/support/sync-reads-worker.ts`，继承真实 Library／Conversation，运行在本地 workerd 的临时 SQLite Durable Object 中。`FixtureResourceMeter` 记录原生 SQL cursor 的 `rowsRead/rowsWritten`；只有此合成夹具额外记录 SQL 模板以定位查询，不记录业务内容、绑定参数或凭据。不访问生产、不创建云资源、不调用模型。

每组先构造数据，再连续测量 30 次热列表查询；通过 `ctx.abort()` 强制重建对象，并断言实例 ID 改变，区分冷构造与后续查询。修订号、持久快照和候选索引都只在夹具中创建，生产结构没有变化。

## 实验一：全量列表与候选读取

| 合成对话数 | 单次完整快照读取 | 冷构造额外读取／写入 | 单次修订号检查读取 | 单次持久快照读取 |
| ---------: | ---------------: | -------------------: | -----------------: | ---------------: |
|          0 |                4 |                93／1 |                  1 |                1 |
|         10 |               61 |                93／1 |                  1 |                1 |
|        225 |            1,351 |                93／1 |                  1 |                1 |
|      1,000 |            6,001 |                93／1 |                  1 |                1 |

每个合成对话均含 metadata、title 和 idle activity；实际生产数据分布不同，不能把 1,351 当作生产每次请求的精确行数。完整快照包含 `list()` 的关联查询、`activity.snapshot()` 和删除游标读取；`after` 当前只是删除游标，不会让对话列表变成增量查询。

以 225 条合成对话、每十秒一次、持续可见 24 小时推算，仅热快照即为 **11,672,640 行／客户端／日**；1,000 条时为 51,848,640 行。若每次都冷构造，还会额外增加 803,520 读取行和 8,640 写入行。这是固定负载模型，不是生产账单预测。

单行修订号与持久快照都能把查询原语降到一行，变更标题后修订号从 1 增至 2，随后完整快照包含新标题。但这里尚未实现完整的修订号同步协议。若仍每十秒唤醒对象，构造成本依然存在；不能宣称改成修订号轮询后整次请求只读一行。

默认选择“变更通知＋单行修订号＋必要时读取当前状态”。整份列表另存单行快照需要重复存储和维护，还受单行大小约束，暂不采用；内存缓存可以加速，但不能依赖其跨休眠存活。

## 实验二：Conversation 冷启动查询

| 已完成消息／run 数 | 原冷构造读取 | 候选索引后冷构造读取 |
| -----------------: | -----------: | -------------------: |
|                  0 |           89 |                   91 |
|                 20 |          128 |                   91 |
|                200 |          488 |                   91 |
|              1,000 |        2,088 |                   91 |

各组冷构造均另有 1 行写入。1,000 条时，以下恢复查询自身读取 2,000 行：

```sql
SELECT runs.* FROM runs
JOIN messages ON messages.id = runs.assistantId AND messages.runId = runs.id
WHERE messages.status IN ('queued', 'running');
```

原查询计划是 `SCAN runs` 后按消息主键查找。现有活动消息部分索引带 `role='assistant'` 条件，当前查询不能使用它。夹具增加：

```sql
CREATE INDEX sync_probe_pending ON messages(status)
WHERE status IN ('queued', 'running');
```

随后计划变为按 `sync_probe_pending` 查询 messages、按主键查询 runs。每个非空场景临时设定一条 queued 和一条 running 消息，建索引前后均返回同样两项，再恢复全部 completed 后重测冷构造。1,000 条终态历史的读取下降约 96%，不再随本组历史大小增长；固定开销中仍包括 `sqlite_master` 的 74 行，未在本轮处理。

这验证了查询与索引方向，没有覆盖活跃工具恢复、取消和重复执行等完整语义，实施时仍须运行相关回归。

## 实验三：控制消息与页面状态

热对象直接调用真实 WebSocket 消息处理器的 60 次结果：

| 控制消息        | SQL 语句 | 读取行数 |
| --------------- | -------: | -------: |
| `session-check` |        0 |        0 |
| `sync-check`    |       60 |       60 |

该实验使用合成 socket，不包含真实网络 ping、握手鉴权和平台休眠。`session-check` 没有 SQL，不代表唤醒后的构造和 CPU 免费；也不能据此认定每次心跳都会冷启动。

使用项目实际 TanStack Query 的 `QueryObserver`，模拟 document/window，四个阶段各 240ms，轮询间隔缩短为 40ms：

| 页面状态                              | 轮询调用次数 |
| ------------------------------------- | -----------: |
| 可见、有焦点                          |            5 |
| 可见、失焦                            |            6 |
| 隐藏                                  |            0 |
| 恢复可见、请求持续失败、`retry:false` |            6 |

次数可能随本机调度小幅变化，断言验证的是“可见时继续、隐藏时停止、错误后 interval 仍继续”。它解释了没有用户操作仍有读取的可能机制：页面可能持续可见。它不是 Safari／PWA 的后台冻结或焦点真机验收。

## 实验支持的修订

1. 取消 Library 的定时全量轮询，复用已认证的通知 WebSocket 发出低频变更通知；重连比较持久修订号，不恢复同步事件历史表。
2. 为恢复任务查询增加待处理消息索引；同时减少 Conversation 的定时数据库游标检查。
3. 保留 Access 到期检查与 Conversation 最多五分钟重验，重验后优先按已有 epoch／seq 恢复，避免每次重新读取全文。
4. 配额／临时失败后退避并保留缓存；`retry:false` 本身不能阻止 interval 持续请求。

具体实施顺序、竞态处理、离线升级与验收条件见[空闲读取修复计划](../plans/durable-object-idle-read-plan.md)。此前的同步 CPU 尖峰和平台观测缺项继续单列，不因本次本地行数实验而视为解决。
