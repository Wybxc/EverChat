## 已定位的原因

### 1. 工具参数错误被误报为供应商流解析错误

`worker/providers/tool-turn.ts` 在 SDK 发出完整 `tool-call` 后执行 `JSON.parse(part.input)`，再调用 `validateWebToolCall()`。两次线上错误的内层文字均来自后一个函数，说明 JSON 已经成功解析；失败发生于应用的参数／目标地址校验。

随后 `worker/providers/events.ts` 的统一异常处理调用 `sdkProviderError()`，后者将应用 `AppError(TOOL_INVALID)` 也转换为 `stage: protocol`、`STREAM_INVALID`，丢失了原错误分类。错误界面因而暗示 SSE 或供应商 JSON 损坏。

两个中断版本的末尾思考均准备读取同一公开 HTTP 地址。`shared/web-tools/tasks.ts` 的 `publicWebUrl()` 仅接受 HTTPS；向真实 SDK 流处理路径输入该 HTTP 调用，可以复现完全相同的错误。

**证据强度：**HTTP 地址策略不匹配是高置信原因，但历史记录没有保留被拒绝调用的实际参数，不能将思考文字等同于工具调用原文。可以确定的是本地工具参数校验失败，而非这两次发生了 JSON 语法解析失败。

DeepSeek 的 [Fetch 文档](https://api-docs.deepseek.com/zh-cn/guides/search/)允许 HTTP／HTTPS、最长 8192 字符；EverChat 只允许 HTTPS、最长 2048 字符。读取接口固定通过 HTTPS 请求 DeepSeek，目标网页是否为 HTTP 是另一项策略，不应混为一谈。

### 2. 一条搜索结果异常会使整批结果失败

`worker/web-tools/service.ts` 逐条处理结果时，任一 URL、标题或摘要不通过校验就直接 `throw invalid()`；此前已收集的有效来源也不会返回。公开 HTTP 搜索结果同样会被拒绝。

最外层 `catch` 又将 JSON 格式、字段缺失、目标地址策略、大小限制和网络错误全部映射为 `INVALID_RESULT`。线上 12 次该类失败无法进一步归因；不能断言它们都是 HTTP 地址导致的。

本地已复现：一个有效来源加一个 HTTP 来源，或加一个缺少标题的来源，都会使整个调用失败。现有测试还主动要求含无效来源的整批响应失败，需要随产品策略一起调整。

### 3. 单次工具超时会终止整个回答

工具服务和 DO 调用外层均设有 15 秒期限。`executeWebTool()` 将信号中止统一返回为 `TIMEOUT`、`terminal: true`；`runWebTool()` 据此停止整个任务，下一条待执行调用也被停止，模型没有机会利用已有资料完成回答。

同一处理还混淆了用户取消、任务期限到达和单次网络超时。单个网页失败与全局停止应采取不同策略。HTTP 404 目前已经能作为非终止结果回传模型，这条路径可以复用。

### 4. 模型看到的工具约束与实际服务不完全一致

搜索 schema 允许 500 字符，但 DeepSeek 服务只接受 128 个 Unicode 字符；URL schema 没有表达实际的协议／目标地址策略。字段不匹配应给模型可修正的反馈，避免直接终止整个回答。

工具定义的 `strict: true` 也不能作为必然符合 schema 的保证。DeepSeek 的 [Tool Calls 文档](https://api-docs.deepseek.com/zh-cn/guides/tool_calls/)要求使用 `/beta` 开启 strict，且不支持 `minLength`／`maxLength` 等约束；此次配置的端点不是该 Beta 端点。不能仅添加 `strict`，也不能未经评估直接切换端点。

## 本地复现

使用现有 `fixtureStream()`、`toolStream()` 和生产 `executeWebTool()`，完成以下 7 个断言场景。供应商协议仍由实际安装的 AI SDK 解析；所有网络响应均为本地构造，未发出真实请求。

1. 合法 HTTPS 工具调用正常形成完整工具轮次。
2. 公开 HTTP 调用产生与线上一致的 `STREAM_INVALID`。
3. 合法 JSON 含额外参数，也产生同一种错误，证明现有文案无法区分校验原因。
4. 同轮一个合法调用、一个 HTTP 调用，整轮没有可执行的 `toolTurn`。
5. 一个有效搜索来源加一个 HTTP 来源，整批返回 `INVALID_RESULT`。
6. 一个有效搜索来源加一个无标题来源，整批返回 `INVALID_RESULT`。
7. 调用者取消也被归为终止性的 `TIMEOUT`。

这些是现有行为的复现，不是修复后的验收结果，也不能还原丢失的历史响应体。

## 建议实施顺序

### P0：修正 URL 策略与搜索结果的失败粒度

- 将“可作为引用的来源地址”“可交给联网服务读取的目标地址”“携带 API Key 的服务端点”分开校验。服务端点继续固定 HTTPS；公开目标支持联网供应商允许的 HTTP／HTTPS。保留凭据、非网页协议、本地／内网目标等边界，不将 HTTP 地址静默改写为 HTTPS。DNS 和重定向目标的网络安全仍由实际抓取服务保证，字符串校验不能替代网络策略。
- 对齐 DeepSeek Fetch 的 URL 长度能力，并根据所用服务生成对应工具参数约束与说明。
- 搜索结果逐条校验。缺少标题可使用域名；摘要选择有效的非空字符串。无法使用的来源单独过滤并附带有界警告，其余有效来源继续使用。根结构损坏仍是响应失败；返回非空结果但全部被过滤时，明确反馈“没有可用来源”，不伪装成正常无匹配结果。
- API Key 泄漏检查仍是硬边界，避免把夹带凭据的来源或错误内容发给用户／模型。不要以“容错”为由忽略完整性、权限或容量保护。

### P1：工具调用局部失败，模型可以修正或收尾

- 区分未校验的候选调用与可执行调用。只有名称、身份、JSON 和业务参数全部通过的调用才能执行；候选失败记录不应被强行转换为合法 `WebToolCall`。
- 对身份明确、流已完整结束，但参数 JSON 或业务参数无效的调用，生成对应调用 ID 的结构化失败结果，把字段路径和预期条件回传模型。已有合法调用继续处理，避免一个错误丢弃整个轮次。
- 保留供应商要求的思考签名／加密续接资料及原始调用身份。原始参数若需用于协议续接，仅在有界的私有结构中保存，并逐协议验证可序列化性；不能安全续接时保留部分回答并明确停止，不伪造缺失 ID、不修补未完整结束的流。
- 单个工具超时、网页不可读和短暂网络错误通常作为局部失败结果；用户取消、全局期限、身份歧义和存储不可用继续停止任务。认证／余额故障停止继续调用联网服务，在剩余预算允许时让模型根据已有资料结束回答。
- 优先让模型根据失败结果调整调用，而非自动重发整段生成。重复的同一错误调用使用规范化参数指纹识别，防止无进展循环；必要时在已有上下文和期限内关闭工具，生成带局限说明的回答。不要重新引入全局固定工具轮数上限。
- 若之后增加只读工具的退避重试，单独设计幂等记账、请求认领与计费边界。优先采用非阻塞调度，不能只在现有 `fetch()` 外套重试：现有任务账本按单次实际请求设计。生产验证额外调用会有费用，应明确记录。

### P2：诊断准确、长期成本可控

- 保留 `TOOL_INVALID` 等应用错误分类；区分 SSE／JSON 解析、SDK schema、工具参数、来源过滤、传输中断与超时。用户提示说明失败阶段，不统一显示“供应商流格式无效”。
- 仅在错误或部分成功时记录有界诊断：调用 ID、工具名、轮次、规则码、字段路径、HTTP 状态、实际字节数、结果有效／丢弃数量和供应商请求 ID。正常路径不逐事件持久化，也不恢复供应商完整原始流日志。
- 默认不记录聊天内容、原始工具参数、网页全文和密钥。必要的失败样本采用显式调试模式、脱敏、严格大小限制和短保留期。历史缺失诊断无法补算为已知原因。
- UI 将“完整完成”和“中断后保留的正式回答”区分；局部工具失败显示在对应工具记录，不覆盖随后成功收尾的回答。
- 若需要调整持久化结构，沿用本地离线运维迁移，不在读取聊天或连接客户端时迁移。保留低频批量写入与现有全局任务期限，资源测量需分别验证本地行为及 Cloudflare Free 实际 CPU／SQL／Workflow 成本。

## 验收条件

- 上述 HTTP 地址可以进入合法的网页工具执行路径；服务密钥只发送到固定供应商 HTTPS 端点。
- 同批搜索结果中部分无效时仍返回有效来源，并保留可解释的过滤原因。
- 同轮合法调用能执行，参数错误调用不会执行，并可回传模型修正；四种供应商协议的调用与结果一一对应。
- 单个网页超时后可尝试其他来源或生成回答；用户取消与全局期限依然立即生效。
- 流损坏、异常 EOF、重复／歧义 ID、缺少续接签名不被当作成功，也不会执行未完成工具调用。
- 部分正文、思考、分支、用量和已完成工具结果在失败后仍保留；不会因重试或恢复重复计费／入账。
- 不引入逐 Token 数据库写入、无限重试、运行时数据库迁移或完整响应日志。
