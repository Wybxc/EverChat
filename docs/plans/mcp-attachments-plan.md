# EverChat MCP 附件功能计划

日期：2026-10-23；2026-10-25 更新。状态：MCP 上传、版本语义与本地辅助程序已实现，完整回归与生产离线升级已完成，PR #10 已合并发布；见[上线记录](../measurements/mcp-production-2026-10-25.md)。网页基础能力见 [R2 直传计划](r2-direct-upload-plan.md)，平台性能排查单列。

2026-10-25 补充：`.typ`、不可变文件版本、沿用／替换、分支活动材料与实际输入回执按[讨论记录改进计划的阶段 C](mcp-discussion-observability-plan.md#c附件版本及沿用替换)扩展，与本专项合并交付，不重复开发上传路径。

## 目标与范围

让自动化调用方能携带图片、文本、代码、CSV 和含文字的 PDF 发起或继续对话。附件、提问和回答保存为网页中的正常对话，沿用分支、上下文管理、后台生成、费用统计和备份；不增加临时聊天模式。

采用「批量签发 R2 预签名 PUT URL → 调用端直传 → 调用聊天」的三步主路径，另提供小文件的纯 MCP 上传工具。MCP 入口复用可撤销 API Key；HTTP 直传由 R2 验证 URL 签名，不向上传程序暴露长期 Key。附件复用私有 R2 和既有附件应用服务。图片缩放和 PDF 提取优先在调用端完成，避免把重计算移到 Workers Free。

不增加上传确认工具或确认请求。`everchat_chat` 在接受生成前，自动校验并保存本次选入的附件；上传 HTTP 成功不直接等于附件已经通过业务校验。

首期不包含 OCR、知识库、外部 MCP 递归调用、任意 URL 抓取，以及模型生成图片／文件的输出能力。以下现状表保留最初调研基线；实现与上线状态以上述记录为准。

## 调研基线

| 位置                                    | 当前行为                                                                                    | 需要补充的部分                                              |
| --------------------------------------- | ------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |

| `worker/mcp/handler.ts`                 | 四个聊天核心工具及只读帮助工具；协议请求体上限为 2 MiB                                      | 上传／读取／删除工具；保留控制消息边界，不把大文件塞进 JSON |
| `worker/mcp/store.ts`                   | 新对话在接受聊天时才创建；续聊按 Key 和精确位置授权                                         | 允许首次提问前准备附件，且重试不重复创建空对话              |
| `worker/attachments/`                   | 原文件和提取文本在 R2，Library 保存元数据、状态、租约和清理信息                             | Key 对文件的明确所有权；复用上传、解析、校验和清理逻辑      |

| `worker/generation/attachments.ts`      | 生成时读取私有 R2，图片校验哈希，文档读取已保存文本                                         | 直接复用，任务不能依赖 MCP 客户端保持在线                   |
| 网页附件入口                            | 新对话首次添加文件就创建普通对话和 URL                                                      | MCP 采用相同语义，无需引入独立的临时文件工作区              |

「文件已保存」不等于「可用于模型输入」：普通原图可能尚未缩放，PDF 原文件也可能还没有提取文本。对外必须区分上传状态与输入准备状态，不能把底层 `Attachment.status: ready` 直接当成可发送。

## MCP 的传输边界

MCP 的工具调用用 JSON `arguments` 传参，工具结果可以携带图片、资源链接和嵌入资源；这不意味着远程服务自动获得调用端的本地文件。当前方案依据 [MCP Tools 规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)设计应用工具，不依赖宿主自动转发附件。

因此，不能让调用方只传 `/Users/.../report.pdf` 或 `file://...` 就认为文件已上传。必须由有文件访问权限的宿主或本地辅助程序读取实际字节并提交。也不把 [Resources 的读取机制](https://modelcontextprotocol.io/specification/2025-11-25/server/resources)当作上传协议。

两条路径共享同一份存储和消息引用：

| 路径           | 适用调用方                                       | 流程                                                                                  |
| -------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------- |
| 二进制主路径   | 自动化脚本、有本地执行能力的 Agent、本地辅助程序 | 批量签发 → 按返回地址 PUT 原文件及 PDF 提取结果到 R2 → `everchat_chat` 自动校验并引用 |
| 小文件工具路径 | 只能调用 MCP 工具、但能提交实际文本或字节的宿主  | `everchat_attachments_put` 提交 UTF-8 文本或 base64 → `everchat_chat` 引用            |

不要求语言模型手工生成大段 base64 或猜测哈希。工具路径的总 JSON 请求仍受现有 2 MiB 上限保护；可用原文件大小由实际编码开销和请求封装共同决定，并由能力发现返回。超过这一边界应走二进制路径，不新增大量 JSON 分片调用。该边界不是原文件或 PDF 全文的新上限。

## 调用流程与工具契约

### 准备文件与目标对话

新增 `everchat_attachments_prepare`：

```json
{
  "uploadId": "33dc5b10-bd4f-49eb-8e12-b477dd32f01d",
  "files": [
    {
      "clientFileId": "71d2f965-c092-450b-afb1-d31223c66040",
      "name": "report.pdf",
      "mediaType": "application/pdf",
      "size": 123456,
      "sha256": "<原文件实际 SHA-256，64 位小写十六进制>",
      "purpose": "document"
    }
  ]
}
```

可选 `continuation` 定位现有对话和父消息；不接受任意网页 `conversationId` 作为授权依据。没有续聊位置时，在 Library 的同一事务中创建一个普通空对话、记录准备批次和文件登记。网页可以看到这个对话，与网页首次添加附件的行为一致；此时尚未创建用户消息、模型任务，也不调用自动标题模型。

`uploadId` 是上传批次的幂等键，独立于聊天的 `requestId`。同 Key、同 uploadId、同规范化清单返回同一对话和文件；清单、文件内容摘要或目标位置改变则返回 `IDEMPOTENCY_CONFLICT`。`clientFileId` 在同一清单内唯一，使文件顺序变化也能稳定识别对象；另行保存展示顺序。

返回 `uploadRef`、`conversationId`、网页 URL，以及每个文件的 `attachmentRef`、上传状态、输入准备状态和 `uploads[]`。每个上传槽位包含 `kind`（`original`／`pdf-text`）、`method: PUT`、完整预签名 URL、必须发送的 `headers` 与 `expiresAt`。PDF 可在同一次准备中声明派生流的准确大小及 SHA-256，服务端一并签发两种槽位；派生流与原文件哈希及解析器版本绑定。

上传示意：

```text
PUT https://<account-id>.r2.cloudflarestorage.com/<bucket>/<unique-object-key>?X-Amz-Algorithm=...&X-Amz-Signature=...
Content-Type: application/pdf
Content-Length: 123456
If-None-Match: *
```

上传请求不附加 EverChat Key、Access Cookie、Access JWT 或额外的长期 R2 凭据。URL 本身是短期上传凭据，必须完整使用、禁止重定向，不记录到应用日志、持久消息或错误详情。签名固定对象、PUT 方法、Content-Type、`If-None-Match: *`；签名头不能由客户端省略或替换。发布前用真实 R2 验证大小约束、签名头被移除／篡改及分块传输的拒绝行为，不将元数据登记或事后检查误写成 R2 写入前的硬限制。

URL 有效期默认 5 分钟，且不超过批次的未完成租约；同一有效批次的 prepare 重试不延长租约。过期且未接受为业务附件的槽位按 `UPLOAD_EXPIRED` 处理，清理后显式使用新 uploadId 准备。已正式保存的附件不因上传 URL 过期而失效。

[R2 预签名 URL](https://developers.cloudflare.com/r2/api/s3/presigned-urls/)只能用于 S3 API 域名，不能套用网站自定义域名；无需公开 bucket 或签发 GET URL。同一 URL 在过期前可重复请求，不承诺一次性消费或按 MCP Key 立即撤销。`If-None-Match: *` 利用 [R2 的原子条件写入](https://developers.cloudflare.com/r2/api/s3/api/#object-level-operations)阻止覆盖已存在的对象；它不是整个 URL 生命周期内的一次性令牌。

### 调用聊天时自动保存附件

预签名 PUT 写入服务端随机分配的唯一对象键，不再从临时键复制为正式键。复用网页的 `prepareAttachmentUploads`／`AttachmentStore.receive`，MCP 另加 Key 和批次授权。调用方完成 PUT 后直接调用 `everchat_chat`：

1. 优先恢复已接受任务，再检查 Key、批次、对话与文件归属。
2. 通过 R2 HEAD 检查存在、大小和 Content-Type；异步 I/O 后再次校验状态。客户端声明的 SHA-256 是内容指纹，不作为上传阶段已验证的摘要。
3. 自动接收并按用途解析；图片在模型准入时校验文件头，生成读取时沿用内容摘要检查；文本和 PDF 派生流沿用编码、索引与提取工作集检查。不为保存原文件下载全文或执行一次完整复制。
4. 全部所选附件就绪后才接受生成。部分失败保留成功文件，允许用原 requestId 重试，不重复调用模型。

签名固定 PUT、唯一键、Content-Type 和 `If-None-Match: *`；不签 Content-Length，浏览器无法主动设置此请求头，大小由 HEAD 在接收时检查。删除登记立即使业务引用失效，对象清理等待固定 URL 到期和在途宽限，不续签旧登记、不重用对象键。URL 5 分钟与 15 分钟宽限不是任意慢上传的硬终止保证，极端迟到对象由离线核对回收。无需新增用户确认步骤。

MCP 工具和内部附件服务直接编排，不通过自身 `/api` 接口转发，也不伪造网页 Cookie、Origin 或 Access JWT。

### 小文件一步保存

新增 `everchat_attachments_put`，接收 `uploadId`、可选 `continuation`，以及文件数组。每个文件包含名称、MIME、`purpose` 和互斥的 `text`／`dataBase64`，可选 PDF `extraction`。`text` 只用于支持的文本类型，按实际 UTF-8 编码保存；二进制严格校验 base64、解码后长度和文件类型。服务端为文件槽位分配稳定 ID，并返回供重试关联使用。

该工具在有界请求中计算大小和 SHA-256，再调用与 prepare 相同的批次准备、上传和解析服务。调用方无需为小文本手算哈希。幂等按解码后的实际内容摘要及元数据判断，不保存 base64 请求副本。

返回值与主路径的批次／文件引用相同。文本保存并解析成功即可发送；PDF 若未一并提供符合现有格式的提取结果，应明确返回 `awaiting_extraction`，不能仅凭原文件已上传就继续模型调用。

### 使用附件提问

扩展 `everchat_chat`，示例：

```json
{
  "requestId": "7782611a-07cd-4757-936c-cc6394df102d",
  "modelRef": "<everchat_models_list 返回的模型 ref>",
  "uploadRef": "<准备或工具上传返回的批次 ref>",
  "prompt": "总结第 2 至 5 页的结论。",
  "attachments": [
    {
      "attachmentRef": "<report.pdf 对应的 ref>",
      "selection": { "pageRanges": [{ "start": 2, "end": 5 }] }
    }
  ],
  "waitMs": 10000
}
```

规则：

- 首次带附件提问用 `uploadRef` 复用准备时创建的空对话；纯文字新建路径不增加准备步骤。该批次首次新建提交绑定一个聊天 `requestId`，并发的新 ID 不能重复使用它创建多条根消息。
- 给已有对话上传时，提交的 `continuation` 必须与准备批次的位置一致。续聊也可再次引用该 Key 在同一对话中已上传的附件；附件不会因整棵树的其他分支有更新而自动改变归属位置。
- `prompt` 改为可省略；有效正文和有效附件至少有一项。仅附件消息的初始标题可取文件名，后续自动标题仍走普通任务流程。
- 同一条消息中附件引用不得重复。`purpose: image` 转为 `imageIds`，文档转为 `fileIds`，选区转为现有 `fileSelections`；服务端从可信保存记录组装引用，不相信调用方自报的 Token 数、解析状态和文件归属。
- 只有本次明确选入的文件需要处于可发送状态。批次中其他文件上传失败时，不阻止使用已完成的文件；不能悄悄忽略请求里选中的失败文件。
- 同 Key、同对话才可复用引用。跨对话附件复制留待后续，首期可明确重新上传，不把一个 R2 对象挂到多个对话而破坏已有删除和备份规则。
- 未指定选区时使用全文；选区超出页码／文本边界、切开 Unicode 代理对或超出上下文预算时明确拒绝，不静默截断或自动切换模型。
- 回答状态、短等待、`runRef`、输出分页、取消与部分回答保留维持现有行为。文件上传成功本身不会触发模型调用。

`selection` 首期支持 PDF 的 1 起始、首尾均包含的 `pageRanges`，以及已有 UTF-16 单元的 `[start, end)` 文本 `ranges`，两者互斥。页码必须依据已保存的全文页码索引转换；服务端规范化选区并固定实际文本哈希。其他文本类型暂沿用现有全文输入，不借本次接入改变其解析边界。

### 状态、预览与删除

| 工具                          | 契约与用途                                                                                                                                                                                      |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `everchat_attachments_get`    | 用 `uploadRef` 或明确的附件引用查询自己上传的文件；返回上传／解析状态、错误、字节数、页数、近似 Token 数与可发送能力。默认只返回元数据；显式请求文本预览时有界分页，避免把全文塞进 Agent 上下文 |
| `everchat_attachments_delete` | 删除自己上传且没有消息或活动任务引用的附件；幂等返回逐文件结果。复用现有引用检查、删除令牌和 R2 清理队列，不提供强制删除已发送资料的选项                                                        |

输入准备状态明确区分 `awaiting_upload`、`awaiting_extraction`、`preparing`、`ready`、`failed` 和 `deleted`，并保留底层上传状态。状态查询可通过只读 HEAD 报告对象已上传，但不把它标为可发送，不续租、不写进度、不触发正式保存或模型生成。正常三步调用不要求先查询。

同域文件路由仅提供带 Key 的 GET／HEAD 正式原文件读取；原文件和 PDF 提取结果的 PUT 都使用 R2 预签名槽位，不新增同域上传代理。读取响应继续采用私有下载头、`no-store` 和 `nosniff`。工具结果不默认回传图片 base64。首期不注册全空间 Resources，也不自动列出网页或其他 Key 的文件。

## 各文件类型的处理

| 类型                | 调用端                                                     | EverChat 服务端与模型输入                                                                    |
| ------------------- | ---------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| PNG／JPEG／WebP     | 保留原图，检查文件头并计算字节指纹                         | 复用文件头、模型输入工作集与读取时哈希校验，视觉能力及上下文检查；由现有 AI SDK 图片路径发送 |
| TXT／Markdown／代码 | 上传实际 UTF-8 原文，不执行代码或预渲染 HTML               | 复用严格 UTF-8、控制字符校验、提取文本保存和文本模型输入                                     |
| CSV                 | 上传原文件                                                 | 复用 Papa Parse 及当前行列、编码和上下文检查，不把表格转为图片                               |
| 含文字的 PDF        | 使用现有版本 PDF.js 提取全文和页码索引，连同原文件分别上传 | 复用来源哈希、解析器版本、编码、页码索引和容量校验；按全文或选区注入文本                     |

PDF 提取结果继续使用现有「小型 JSON 元数据行 + UTF-8 正文流」格式，通过 `application/vnd.everchat.pdf-text` 直传到独立 R2 临时槽位，避免大 JSON 和大 RPC 参数。调用聊天时由现有解析服务校验并保存。服务端验证其与声明的原文件哈希绑定，不宣称独立证明提取文字与 PDF 的语义一致；这与网页当前信任边界相同。

不把 PDF.js 或图片转码器放入 Worker／DO；不调用付费解析、OCR 或图片转换服务。纯 MCP 宿主若不能执行本地预处理，可以直接发送符合要求的小图片和文本；PDF 需由宿主或辅助程序完成提取。

提供可选本地辅助程序，负责读取用户指定文件、处理图片／PDF、计算哈希、上传并输出引用，减少每个自动化集成重复适配。建议放在 `scripts/mcp/`，提供一个 `pnpm mcp:attachments` 入口，协议实现复用官方 MCP 客户端：

- PDF 使用已安装的 `pdfjs-dist`。抽取共用的文字／页码索引生成逻辑，浏览器 Worker 和 Node 的加载、取消、资源访问及错误转换留在各自适配层。[PDF.js 官方示例](https://mozilla.github.io/pdf.js/examples/)提供 Node 使用入口；实施前先验证当前锁定版本在项目 Node 环境下的字体资源、Worker 和取消行为。
- 图片沿用当前原图政策，不为 MCP 新增强制转码或 sharp 依赖；可由调用端自行缩小文件后重新计算指纹。
- 辅助程序自行调用 MCP 时，Key 从环境变量或进程内配置读取，不放命令行参数、输出 JSON、URL 或文件正文；由 harness 管理 MCP 凭据时，上传步骤只需使用工具返回的预签名 URL，无需提取其 Key。上传端核对配置的 R2 HTTPS 主机、禁止重定向，并严格发送返回的签名头；绝不向 R2 附加 EverChat Key。进度只写本地标准错误输出，普通结果不含文件正文或完整预签名 URL。

## 模型能力与现有容量

扩展 `everchat_models_list`：返回附件服务是否配置、允许 MIME、当前上传／单消息／上下文边界、inline 请求体边界；每个模型补充图片能力、来源及是否允许尝试。PDF／文本输入属于应用层提取能力，不伪装成供应商原生 PDF 能力。

图片能力判断复用现有 `canAttemptCapability`：明确不支持时拒绝；未知能力保留当前可尝试策略和实际请求诊断。不能把目录缺失误判为明确不支持，也不能在失败后去掉图片继续回答。

本计划沿用代码中的既有边界，不新增 MCP 专属的每日文件数、字符数或调用轮次限额：

共享边界以[当前资源政策](../architecture/free-tier-resource-policy.md)和代码为准：原文件仍为每文件 100,000,000 字节；不设置每日上传次数、累计附件容量或数量、每消息图片／文档数量限额。不再强制缩图至 1536px／1 MiB。解析及模型请求仍有各自内存工作集、模型窗口和显式预算约束。PDF 提取全文后选择页码或片段，上传等待为客户端 60 秒、签名 5 分钟。原文件直传不受 Worker 请求体边界，但本轮保留现行共享单文件政策，不顺带放大浏览器或模型工作集。

## 鉴权与持久化边界

MCP 工具和 `/mcp/attachments/*` 私有读取请求使用相同的 Bearer Key 验证和同源 Origin 规则，不接受 Cookie、文件路径或附件引用代替鉴权。仅 R2 直传使用 URL 中的 SigV4 签名；签名不会授予 MCP 工具、网站 API 或下载权限。API Key 管理接口仍由 Access 保护。

- 所有权明确到 `keyId + attachmentId + conversationId`。仅知道对话 ID、批次 ref 或附件 ref 不能读取文件；不能通过「列出该对话所有附件」获得网页后来上传的文件。
- 删除 Key 立即拒绝其新签发、聊天调用、正式保存、读取、查询和删除。已经签发的 PUT URL 仍可能在过期前写入其固定对象键，但不能被撤销 Key 接受为业务附件或提交生成。已接受的后台回答和已保存普通对话保留；不会因为撤销自动删除模型仍需读取的资料。
- 上传／解析在异步 I/O 后、确认成功前再次检查 Key、文件及对话的状态。撤销或删除与上传交错时，不把未经确认的对象发布成可读／可发送状态，交给现有租约和清理机制回收；已可靠保存的文件不因凭据撤销自动删除。
- 拒绝远程 URL、`file://`、本地绝对路径、目录遍历及非允许类型；不新增服务端任意抓取能力。文件内容始终作为资料而非指令，模型调用沿用现有资料边界说明。
- 直传地址到达 R2 S3 API，不受网站 Access 登录保护，由签名鉴权；bucket 保持私有。MCP 和下载地址须到达 Worker。当前 Access 只覆盖 `/api`、`/auth` 时通常无需改变；若部署使用精确 `/mcp` Bypass，还要明确覆盖私有读取子路径。禁止为附件放开 `/api/*`。`wrangler` 已有 `/mcp/*` 的 Worker 优先规则，SW 也已排除该前缀；仍须做生产回归。

服务端新增用于签名的 R2 S3 凭据，按目标 bucket 收窄权限，仅存于 Worker secrets；现有 R2 binding 不提供可用于 SigV4 签名的 secret。使用成熟的 SigV4 实现，不手写签名，不在仓库硬编码账户、bucket 或凭据。能力发现明确报告签名配置是否就绪。浏览器直传需要单独配置 R2 CORS，限定实际使用的来源、PUT 和签名头；Shell 上传不依赖 CORS，CORS 也不能代替鉴权。

在 Library 中增加小型批次／所有权记录，保存 Key ID、批次与文件 ID、目标对话／位置、规范化指纹、首次提交绑定及状态，以及对象键、固定签名过期时间和清理租约；为 Key 和批次建立索引。不保存完整预签名 URL。二进制、base64、提取全文和供应商请求均不进该表，也不增加逐 chunk 上传日志。消息只保存现有不可变 `ImagePart`／`DocumentPart` 引用。

批次指纹与聊天指纹分别管理。聊天指纹包含有序附件身份、源哈希、选区和对应提取版本；只允许等待时间变化。规范化不改变附件展示顺序。重放已接受请求时先返回原任务，再考虑当前文件／模型设置，避免重放变成新模型调用。

跨 Library／Conversation 不新增分布式事务承诺：在 Library 内事务完成准备、文件授权和首次请求绑定，再通过既有提交去重／对账恢复 Conversation 接受结果。发送前复用 `pinAttachments` 及上下文校验；恢复、通知、费用记录仍由原有任务系统负责。

新增表、字段和存储版本只通过[本地离线运维迁移](../operations/offline-storage-migration.md)引入。旧附件不猜测归属、不自动赋予 MCP 权限，也不在请求中回填。现有 `mcp_requests` 的旧记录无需补附件信息；是否修改 Conversation 物理 schema 以最终差异为准，不能为“以防万一”增加在线兼容层。

## 失败、重试和清理

| 情况                   | 行为                                                                                                                      |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| 上传响应丢失           | 可直接调用聊天，由服务端检查对象并自动保存；也可只读查询。已存在槽位重传返回 412 时不能直接视为业务成功，仍由聊天准入校验 |
| 一批中部分失败         | 保留各文件独立结果；只重传未确认的部分。若底层登记已终止，使用新 uploadId 准备，不覆盖已保存的字节或提取结果              |
| 上传已完成、解析未完成 | 聊天调用内自动校验和解析；缺少派生流返回 `PDF_EXTRACTION_REQUIRED`，处理中返回 `preparing`，不得提前创建模型任务          |
| URL 过期／Key 撤销     | 不再签发或接受相应无效请求；已签 URL 不承诺即时撤销。迟到的 PUT 仅产生待清理临时对象，不得覆盖正式文件                    |
| 对话忙碌               | 返回既有 `CONVERSATION_BUSY`，保留已上传文件；重试原请求，不隐式另建对话                                                  |
| MCP 客户端断开         | 未完成上传由租约回收；已保存文件保留。已接受生成继续在后台运行                                                            |
| 文件被消息或生成引用   | 返回 `ATTACHMENT_IN_USE`；不强制删除，不破坏旧分支和后续提问                                                              |
| 上传后没有发送         | 按普通对话文件保留，可由网页或所属 Key 删除；不新增会静默删除 ready 文件的保留策略，也不自动删除用户可能已操作的空对话    |

错误沿用 MCP 的 `code`、`stage`、`retryable` 与可用 HTTP 状态，并附可安全返回的文件引用；补充 `ATTACHMENT_NOT_READY`、`ATTACHMENT_ACCESS_DENIED`、`PDF_EXTRACTION_REQUIRED`、`UPLOAD_EXPIRED` 等明确分类。R2 的 HTTP／XML 错误由调用端保留状态和脱敏诊断，区分签名不符、过期、条件写入失败与网络结果未知；不将上传 2xx 或 412 自动等同于模型输入就绪。错误不返回文件正文、Key、完整签名 URL 或内部 R2 地址。

现有 MCP 会把提交拒绝保存为终态失败。实施时需区分「明确尚未接受、可恢复的准入错误」与永久失败：文件未就绪和对话忙碌不能永久固化原 requestId，调用方排除条件后应能用原输入和原 ID 再提交；已经接受或结果未知时，先对账原提交，绝不重新调用模型。批次首个请求绑定也要与这一状态一致，不能让一次文件未就绪检查占死整个批次。

未完成登记、删除失败等复用 Library Alarm 的有界清理与退避。保留清理记录至签名过期及在途宽限后，再删除对象；已经接收的 ready 文件不会自动到期。唯一键不重用，删除与接收交错时删除获胜。极端慢 PUT 可能在宽限后才完成，离线运维核对孤立对象；不能给正式文件前缀设置会误删正常附件的生命周期。批次记录清理仍应防止旧 uploadId 被重建为新业务。

## Cloudflare 免费层与网络开销

Workers Free 当前每请求 CPU 预算为 10 ms、内存为 128 MB；CPU 与网络等待时长不同，不能据此声称较大文件的校验和 JSON 编码没有成本。[Workers 官方限制](https://developers.cloudflare.com/workers/platform/limits/)

二进制字节由调用端直接进入 R2，Worker／Library 只批量登记、签名和 HEAD 接收，不下载全文验证上传哈希，也不再执行临时 GET、正式 PUT 与临时删除。后续模型读取、文档解析和备份仍有实际 I/O／CPU 成本。普通 Worker 不运行 PDF／像素解码。不能把本地通过等同于平台 CPU 节省已测量。

一批文件只做一次元数据准备，各文件并行上传使用低并发；原文件和 PDF 派生流分别直传，在一次 `everchat_chat` 中完成所选文件的自动校验、保存与生成接受。正常路径没有确认或状态轮询往返。准备和 PUT 不触发付费模型请求，只有显式聊天调用会发起生成。

直传主要省去 Library DO 等待客户端慢上传的活跃时间；普通 Worker 的网络等待本来不计 CPU。每文件主要新增一次 R2 PUT 和接收 HEAD；读取、派生文本及清理操作仍计量，所有额度为全账户共享，不能承诺零费用。

不新增 Worker、DO namespace、Workflow、分块对象清单或逐进度 SQL 写入。成功文件幂等重试不再 PUT；同一模型请求内复用已有附件读取缓存；不跨用户／对话做全局哈希去重。

R2 Standard 的免费额度仍是全账户共享的每月 10 GB-month、100 万次 Class A、1,000 万次 Class B，超额可能收费。输入文件、派生文本、预览、生成读取和备份都纳入用量评估；不把无出口流量费用误写成无读取费用。[R2 官方定价](https://developers.cloudflare.com/r2/pricing/)

## 实施顺序与验收

| 阶段                  | 工作                                                                                                 | 完成标准                                                                                                           |
| --------------------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| A：契约与调用端验证   | 定义工具 schema、批次／所有权、SigV4 签名、错误和能力发现；试跑 Node PDF.js 与原图检查；辅助程序原型 | 本地文件通过现有校验；真实 R2 验证签名头、元数据大小检查、过期和条件 PUT；明确目标宿主文件传递边界                 |
| B：上传与聊天闭环     | 离线迁移方案、批量签发、R2 直传、聊天准入内自动保存、状态查询、仅附件消息                            | 仅签发／上传／调用三步即可完成；各种附件进入实际模型请求；旧 URL 无法覆盖正式文件，断开不影响已接受任务            |
| C：工具路径与生命周期 | inline 上传、预览分页、安全删除、租约／撤销／重试；完善本地辅助程序和文档                            | 不支持额外 HTTP 的宿主可提交小文本／图片；并发删除、Key 撤销、响应丢失和实例重置都不造成越权、误删或重复生成       |
| D：发布与平台验证     | 通过 PR 快速检查，独立运行附件／MCP 浏览器回归；离线迁移后部署，核对 Access 和 PWA                   | 匿名不可读，合法 Key 无需 Access 邮箱／GitHub 会话；网页旧附件和 MCP 普通对话完整；记录实际 CPU／R2 操作和证据边界 |

必测场景：

1. 仅附件／混合提问、首次创建、精确分支续聊、换模型、历史附件重新进入上下文、摘要、复制和 ZIP 备份恢复。
2. 四类现有供应商协议的附件输入格式；明确无视觉能力、未知能力、缺少存储和上下文不足时都给出准确结果。
3. UTF-8／中文文件名、CSV 引号与换行、PDF 全文及页码／片段选择、乱码／损坏／加密／无文字 PDF、超大原图及坏图片。
4. 同 uploadId 重放与冲突、批次首次提交竞争、同 requestId 带附件重放与冲突；未知结果只恢复原任务，模拟供应商调用次数不增加。
5. 跨 Key／网页附件引用、伪造元数据、目录遍历、浏览器 Origin／R2 CORS、上传重定向、签名头移除／篡改、超长／短体／分块上传、签名 URL 脱敏，以及附件引用不能作为下载授权。
6. 部分上传失败、没有确认请求也能完成聊天、并发自动保存、准入失败后原 requestId 重试、取消、未发送文件、使用中删除拒绝、对话删除、R2 删除失败后恢复，以及 SW 不缓存文件。
7. 旧 URL 重放、删除后重新 PUT、过期前开始的迟到上传、Key 撤销与保存交错、正式附件不可覆盖、极端迟到对象的离线核对，以及存储与各类 R2 操作的实际用量。

本地功能测试使用模拟供应商和本地 R2／DO，不消耗真实模型费用。按新的 CI 分层，格式／类型／单测／运维集成为 PR 门槛，MCP 与附件完整浏览器回归单独运行并报告。平台资源与真实模型功能须另行获得实测证据，不能从本地通过推导免费层余量或生产性能。
