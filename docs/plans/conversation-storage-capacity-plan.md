# 对话存储容量报错：原因与改进计划

日期：2026-10-18。状态：完成源码定位与平台文档核对，修复待实施；未读取出错对话的私人内容或线上数据库统计。

## 已确认的触发条件

「这个对话已达到存储容量限制。已保留保存的内容，请新建对话继续。」由 `worker/platform/resource-limits.ts` 的 `DATABASE_LIMIT_MESSAGE` 定义，是应用自己的保护，不是 DeepSeek 的模型上下文错误，也不直接证明 Cloudflare 免费账户额度已经耗尽。

| 阶段                                 | 当前判断                    | 结果                                             |
| ------------------------------------ | --------------------------- | ------------------------------------------------ |
| 新发送、重新生成、摘要或手动编辑回答 | `sql.databaseSize > 16 MiB` | 拒绝新增任务／版本，返回 507；已有消息可读取     |
| 普通公开流提交及工具私有流提交       | 超过约 30 MiB               | 阻止继续写流，结束生成并尝试保存已经持久化的前缀 |
| 终态事务                             | 超过 32 MiB                 | 回滚超限事务；不能把尚未可靠保存的尾部标成完成   |

准确常量为 `MAX_DATABASE_START_BYTES`、`MAX_DATABASE_WRITE_BYTES`、`MAX_DATABASE_BYTES`。判断位置在 `worker/conversation/durable-object.ts` 的 `submit`、`reviseAssistant`、`commit`、工具私有流保存及 `finish`。同一条提示覆盖多个阶段，所以仅凭文案无法判断本次究竟撞到了哪个阈值。

独立保护还包括接受任务前 **全部历史 JSON 4 MiB**、每条正文与思考共用 **768 KiB**、每对话 **1,000 条记录**。前者对应另一条「历史容量」提示；分支切换、修改模型上下文窗口或做摘要不会消除这些存储检查。[现行政策](../architecture/free-tier-resource-policy.md)

Cloudflare 文档列出 Free 账户 DO SQLite 合计 5 GB，存储超限说明另列 Free 单对象 1 GB，SQL 单字符串／BLOB／整行 2 MB；16／30／32 MiB 均远低于这些平台边界。平台的 `SQLITE_FULL` 在本项目走另一条「云端存储额度不足」映射，不能和本条应用保护混用。[DO 限制](https://developers.cloudflare.com/durable-objects/platform/limits/)

## 为什么看起来不大的对话也可能触发

`databaseSize` 是当前整个 SQLite 数据库的字节数，不是界面当前分支的可见正文大小。[API 定义](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/#databasesize)

数据库包含所有分支和修订、正文与思考、工具结果、幂等请求记录、执行状态、同步事件、索引及运行中的流日志。暂存的任务上下文和底层页分配也会影响体积；不能按页面文字数推断数据库大小。

已经确认的放大路径：

1. `commit()` 同时把公开流批次写入 `stream_commits` 和 `events`，同一批原始协议有两份用途不同的保存。协议体积还可能大于最终显示的正文与思考。
2. 终态通过 `StreamJournal.compact()` 将正文和思考写入消息，并删除该轮 `stream_commits`；**不是完全没有日志整理**。但 `events` 只按最新约 500 条保留，没有按字节管理，同步历史可能继续保留原始批次。
3. 终态也会把 `runs.config/context` 清空；这不等于删掉所有历史执行记录、同步事件或底层元数据。删除数据后，`databaseSize` 不应被假定立刻按正文净字节同比下降，需要在原生运行时和真实平台分别验证。
4. 修改历史提问、重新生成和手动修改回答都保存新版本；未展示的旧分支仍占存储。摘要缩短的是后续模型上下文，旧消息会继续保存，摘要本身还会增加记录。

以上是源码支持的机制，不是已经测得用户这个对话的占用分布。本次具体诱因需要第 1 阶段的只读统计才能确定。

## 当前可以怎么继续

- 最稳妥：把当前任务的必要背景或简短摘要带入新对话，原对话保留作查阅。已经显示容量错误的回答不能假定尾部全部保存。
- 如果消息净内容仍小，可尝试现有「复制对话」或消息下的「复制到新对话」；新对象不会复制旧原始流、执行表和同步事件。消息入口复制到选定路径为止，通常比复制整张分支图更轻。复制及恢复有自己的消息／备份检查，后续发送仍受历史和数据库保护，不能承诺一定恢复可继续状态。
- 原对话可先导出备份。删除不需要的消息可能减少净内容，但仍保留分支连接、删除标记和必要幂等记录，不能当作可靠的数据库压实按钮；不自动删除旧分支。
- 仅改变模型、减少发送给模型的条数或创建历史摘要，无法直接解除这条物理数据库保护；升级 Workers 套餐也不会自动改变代码中的 16 MiB 判断。

## 修复原则

先减少重复数据和错误拒绝，再扩大容量。继续使用现有低频持久化与客户端高频显示，不加应用每日用量限制、不换套餐、不引入新收费存储来绕开问题。

单对话预算不能代表账户剩余空间。旧策略的 128 × 32 MiB 已约为 4.295 GB，接近 5 GB 总额，还没算 Library、搜索及其他部署；不能直接把每对话改为 1 GB 并宣称仍受免费层兜底。

Cloudflare Free 的 DO SQLite 当前为每日 500 万行读、10 万行写；DELETE 也计写入。统计和维护必须按需、批量执行，不能在每个 Token 或每次预览上扫描全库或做清理。[DO 定价](https://developers.cloudflare.com/durable-objects/platform/pricing/)

## 实施顺序

### 1. 明确原因与只读统计

- 给错误增加稳定代码及阶段：准入预算、流写入预算、终态预算、历史快照过大、平台存储不足；不只让前端判断中文字符串。
- 在鉴权接口按需提供 `databaseBytes`、消息及版本数量、正文／思考／工具结果净字节、`events` 行数与负载字节、公开／私有流字节、仍保留的上下文字节、任务状态。只返回计数，不返回正文或密钥。
- 使用可重复的合成长流与多版本数据，测量生成中峰值、完成后、清理后及重新实例化后的差异。验证可用的 SQLite 页统计；不预设 DO 支持 `VACUUM`、任意 PRAGMA 或本地 SQLite 的维护方式。
- 记录是否为「数据仍多」或「冗余／分配高水位」，避免建议用户反复删除正文却无法恢复。

### 2. 优先整理同步事件与临时流

- 将 `events` 从仅保留 500 条改为同时有字节窗口；用事务内维护的计数和分批回收，避免每次提交做全表求和。
- 已可靠固化为终态消息的原始批次可退出事件窗口。当前 WebSocket 对过旧游标已有全量快照回退；保留单调递增的 seq 和有效事件锚点，不能删空后让序号归零或让客户端误判已同步。
- 回收必须发生在消息、终态事件和相关任务状态可靠落库之后；跨设备、旧游标重连、取消、故障前缀和正在运行的工具私有续接均需回归。
- 继续清理终态上下文和无需保留的私有原始流。运行中的检查点、幂等身份及仍被任务引用的数据不能提前删除。

这一阶段减少长期保留量，但不承诺所有已膨胀对象立即缩小；若物理大小不下降，进入下一阶段的准入与对象整理方案。

### 3. 替换过于粗糙的容量准入

- 不再仅凭 `databaseSize > 16 MiB` 判定对话永久不可继续。准入结合有效数据、可复用空间（须原生验证）、本次输入／上下文的实际字节与终态所需余量；所有检查覆盖普通聊天、修订、摘要和工具。
- 过渡版本可提高过低的准入水位，但保持单对象受控总预算并验证失败前缀可保存。具体阈值以第 1 阶段峰值测量为依据，不直接把 16 改成 1,024 MiB，也不同时放大对话数量和数据库预算。
- 对仅有分配／冗余高水位的旧对象，优先利用可复用空间；必要时提供显式「整理并复制当前路径」操作，先完整验证目标，再供用户切换，保留原对象。保持原 URL 的底层对象切换需要对象别名、写入冻结和引用迁移，不能伪装成一次普通 SQL 清理。
- 平台真正拒绝写入时仍明确失败并保留已持久化前缀；不把配额错误归因于供应商，不自动重发模型请求。

### 4. 支持更长对话，之后再放宽长期预算

- 消息正文、分支元数据及历史分页分离；按当前父链构建模型上下文。历史页、快照、搜索定位、复制和备份均使用有界批次。
- WebSocket 旧游标恢复改为元数据快照加按需内容，控制 JSON／内存／传输峰值；不能只取消 4 MiB 检查，继续全量拼接所有分支。
- 大内容分块保存，仍满足 SQL 单行 2 MB；按实际数据和部署容量规划放宽历史及对话预算，保留单次任务时间、背压和失败保存空间。
- 账户用量采用 Cloudflare 监控与有动作的告警；按需聚合应用诊断，不构建新的高频账户扫描。5 GB 是账户所有对象共享的容量，不承诺由一个应用掌握全部剩余额度。

## 验收目标

1. 合成长协议／小正文、多轮修订和联网工具能够复现旧保护，统计明确指出主要占用；不使用私人对话作测试夹具。
2. 在低于有效数据预算且有足够可用空间时，超过旧 16 MiB 的对象可以继续对话；确实没有余量则在发起付费请求前拒绝。
3. 完成后不长期保留可由终态消息重建的大量原始流副本；事件保留字节满足设置的窗口，seq 和旧游标恢复正确。
4. 停止、断网、DO 重置、事务失败、平台配额错误均保留可信前缀且不重复调用供应商；旧分支和手动版本不丢失。
5. 长对话分页后，首次打开、切换版本及继续生成不再全量解析所有正文；复制、备份、搜索、删除、附件引用及跨设备同步正确。
6. 记录 SQL 行读写、数据库峰值、CPU 和重连传输量，相同输入下不增加每 Token 写入；本地结果不能代替真实平台免费额度测量。

推荐先实施第 1–3 阶段解决当前体验问题，再做第 4 阶段的长期容量提升；[DeepSeek 联网适配](deepseek-web-tools-plan.md)复用同一套存储与执行保护。
