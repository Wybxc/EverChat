# 对话存储容量报错：原因与改进计划

日期：2026-10-18。状态：状态同步、规范内容检查点、分页读取、选定父链加载和容量调整已实现；本地回归及测量结果见末节。前文保留改造前诊断，不代表现行阈值；未读取私人对话或线上数据库。

## 架构结论

数据库保存对话当前的权威状态、用户需要保留的历史版本，以及确保后台任务正确执行所需的最小恢复状态。客户端恢复到当前状态，不需要重放曾经发生过的所有同步通知。

**目标是移除持久化的 `events` 同步历史，而非继续优化它的 500 条保留策略。** 同步改为「当前状态基线 + 在线推送 + 版本校验后重新取状态」。运行中的生成检查点、请求幂等记录和跨组件待办另有正确性用途，不能随着事件表一起删除。

此前计划中的「给事件表增加字节窗口」降为必要时的短期止血措施，不作为最终架构。计划不要求兼容旧的同步协议；新协议、客户端缓存和现有对象的升级需要一次性明确处理，已有对话、分支和消息仍必须保留。

## 已确认的触发条件

「这个对话已达到存储容量限制。已保留保存的内容，请新建对话继续。」由 `worker/platform/resource-limits.ts` 的 `DATABASE_LIMIT_MESSAGE` 定义，是应用自己的保护，不是 DeepSeek 的模型上下文错误，也不直接证明 Cloudflare 免费账户额度已经耗尽。

| 阶段                                 | 改造前判断                  | 结果                                             |
| ------------------------------------ | --------------------------- | ------------------------------------------------ |
| 新发送、重新生成、摘要或手动编辑回答 | `sql.databaseSize > 16 MiB` | 拒绝新增任务／版本，返回 507；已有消息可读取     |
| 普通公开流提交及工具私有流提交       | 超过约 30 MiB               | 阻止继续写流，结束生成并尝试保存已经持久化的前缀 |
| 终态事务                             | 超过 32 MiB                 | 回滚超限事务；不能把尚未可靠保存的尾部标成完成   |

准确常量为 `MAX_DATABASE_START_BYTES`、`MAX_DATABASE_WRITE_BYTES`、`MAX_DATABASE_BYTES`。判断位置在 `worker/conversation/durable-object.ts` 的 `submit`、`reviseAssistant`、`commit`、工具私有流保存及 `finish`。同一条提示覆盖多个阶段，所以仅凭文案无法判断本次究竟撞到了哪个阈值。

独立保护还包括接受任务前 **全部历史 JSON 4 MiB**、每条正文与思考共用 **768 KiB**、每对话 **1,000 条记录**。前者对应另一条「历史容量」提示；分支切换、修改模型上下文窗口或做摘要不会消除这些存储检查。[现行政策](../architecture/free-tier-resource-policy.md)

Cloudflare 文档列出 Free 账户 DO SQLite 合计 5 GB，存储超限说明另列 Free 单对象 1 GB，SQL 单字符串／BLOB／整行 2 MB；16／30／32 MiB 均远低于这些平台边界。平台的 `SQLITE_FULL` 在本项目走另一条「云端存储额度不足」映射，不能和本条应用保护混用。[DO 限制](https://developers.cloudflare.com/durable-objects/platform/limits/)

## 为什么看起来不大的对话也可能触发

`databaseSize` 是当前整个 SQLite 数据库的字节数，不是界面当前分支的可见正文大小。[API 定义](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/#databasesize)

数据库包含所有分支和修订、正文与思考、工具结果、幂等请求记录、执行状态、同步事件、索引及运行中的流日志。暂存的任务上下文和底层页分配也会影响体积；不能按页面文字数推断数据库大小。

已经确认的放大路径：

1. `commit()` 同时把公开流批次写入 `stream_commits` 和 `events`，同一批原始协议有两份用途不同的保存。协议体积还可能大于最终显示的正文与思考。
2. 终态通过 `StreamJournal.compact()` 将正文和思考写入消息，并删除该轮 `stream_commits`；**不是完全没有日志整理**。但 `events` 只按最新约 500 条保留，没有按字节管理，同步历史可能继续保留原始批次。
3. 终态也会把 `runs.config/context` 清空；这不等于删掉所有历史执行记录、同步事件或底层元数据。删除数据后，`databaseSize` 不应被假定立刻按正文净字节同比下降，需要在原生运行时和真实平台分别验证。
4. 修改历史提问、重新生成和手动修改回答都保存新版本；未展示的旧分支仍占存储。摘要缩短的是后续模型上下文，旧消息会继续保存，摘要本身还会增加记录。
5. `submissions.fingerprint` 实际存储完整序列化输入／设置，手动编辑回答也保存完整编辑文本，并非固定长度哈希；这是另一份不必要的正文副本。

以上是源码支持的机制，不是已经测得用户这个对话的占用分布。本次具体诱因需要第 1 阶段的只读统计才能确定。

### 本地合成复现

复用现有 schema、`GenerationBuffer`、`StreamJournal` 和 `ConversationMessages`，在本地内存 SQLite 中构造同一提问下的回答版本。每条回答包含 8,000 个 199 字节的合成 SSE 帧，每帧只有「思考」两个汉字的有效增量；最终正文与思考约 47 KiB。不调用供应商，不使用私人内容。

完成 7 个版本后，消息净文本为 336,117 字节，事件负载为 15,401,515 字节，SQLite 分配为 18,370,560 字节。第 8 次开始前已越过代码的 16 MiB 准入线。为观察完整分布而绕过准入继续到 10 个版本时，净文本为 480,162 字节、事件负载为 21,648,311 字节、SQLite 分配为 24,924,160 字节。

该复现证明存储放大足以造成少量版本触顶；本地 SQLite 页分配不能代替 Cloudflare 原生测量，也不能据此认定线上出错对话具有同样分布。

## 重建对话实际依赖什么

当前代码已经能从消息表及必要的活跃流状态构建完整快照。`ConversationMessages.snapshot()` 读取消息、设置、活动状态，只有快照的 `seq` 来自事件表；当前生成中的消息由 `StreamJournal.materialize()` 补齐。客户端 `useConversation` 在建立 WebSocket 前也已经先请求一次该快照。[服务端快照](../../worker/conversation/messages.ts)、[客户端连接](../../src/features/chat/useConversation.ts)

| 场景                   | 必要数据                                                                 | 同步事件历史的作用                                                       |
| ---------------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------ |
| 新客户端首次打开       | 当前消息／分支、设置、生成状态；生成中的可靠前缀及解析检查点             | 不需要；直接读取当前状态即可                                             |
| 旧客户端重连           | 本地版本与服务端版本；有变化的消息最新状态和删除标记，必要时重新获取基线 | 当前实现用事件回放补差，但这只是一个传输优化，不是恢复的必需条件         |
| 在线查看流式回答       | 当前可靠检查点、其后尚未提交的有界预览尾部、后续实时数据                 | 在线通知可以直接推送，不必为了推送另存一份历史                           |
| DO 实例重启            | 已提交的输出前缀、任务状态、取消意图、工具续接所需状态                   | 不能靠事件恢复原来的供应商连接；当前代码也会把失去连接的普通生成标为中断 |
| 后台任务和外部投影恢复 | 已接受／已认领／已完成状态、待执行引用和最小幂等依据                     | 需要事务性任务状态或待办，不能与可丢弃的 UI 同步通知混为一谈             |

事件回放能减少部分短暂重连的传输量。GET 快照和 WebSocket 订阅之间可能产生的新变更，目前也由事件回放补齐；删除事件表时必须用新的订阅握手处理这个竞态，不能直接删除回放代码后只保留推送。

## 数据库的持久化边界

| 数据                                             | 保存方式及期限                                                                                                                                 |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 用户消息、回答、思考、摘要及手动修改的版本       | 长期保存唯一权威内容；分支通过 `parentId`／`revisionOf` 引用共享祖先。旧版本属于用户历史，不是应清除的同步垃圾                                 |
| 对话标题、设置、置顶及附件引用                   | 保存当前值及必要版本；附件二进制继续沿用现有附件存储，不在 SQLite 再存一份                                                                     |
| 引用来源、可展示的工具调用与结果、生成统计和错误 | 保留有用户价值的最终信息；公共展示和下一轮续接引用同一份结果，不保存多份完整公开载荷                                                           |
| 活跃生成的可靠前缀与解析状态                     | 低频事务持久化；正文／思考本身就是消息的当前状态，不另存一份累计快照。保留恢复解码所需的未完成帧、UTF-8 尾部和协议状态；结束后回收解析临时资料 |
| 任务接受、认领、取消、依赖和调度状态             | 运行期间保存，保证不会丢掉已接受任务或在重入后再次发出同一次请求；结束后仅保留必要状态和结果引用，清除完整上下文和私有配置                     |
| 工具私有续接、签名及加密推理项目                 | 仅在当前任务后续轮次仍需要时保存，不能从显示文本可靠重建；不暴露给客户端，任务终态清理                                                         |
| 请求去重信息                                     | 保存固定长度的规范输入哈希、请求 ID 和结果引用，不保存完整输入。保留范围必须覆盖既有请求的重试，不能随意按短 TTL 删除后导致重复调用            |
| 搜索、Library 活动投影及 Workflow 的待处理工作   | 保存小型、可合并的事务性待办或脏标记，处理成功后清理；投影可重建，不能把全部消息正文包装成另一套通知历史                                       |
| 对话／消息的持久化版本号和删除标记               | 保存用于状态比较、缓存失效和防止旧客户端恢复已删除内容；版本号不再依赖事件表的 `MAX(seq)`                                                      |
| 预览批次、推送包、确认包、连接游标及背压窗口     | 不作为对话业务数据入库；保存在连接／运行时的有界状态中，丢失后重新协商基线                                                                     |
| 完整 SSE 协议、完整同步事件历史及重复终态消息包  | 不长期保存。调试指标只记录计数和必要脱敏信息，不能以调试为由默认保留每条原始响应                                                               |

供应商配置及密钥仍按现有设置范围保存；这里删除的是对话执行期间不再需要的配置副本，不是删除用户的供应商设置。草稿、离线缓存和当前展开状态继续按各自产品需求由客户端管理，不混入同步事件存储。

## 当前可以怎么继续

- 最稳妥：把当前任务的必要背景或简短摘要带入新对话，原对话保留作查阅。已经显示容量错误的回答不能假定尾部全部保存。
- 如果消息净内容仍小，可尝试现有「复制对话」或消息下的「复制到新对话」；新对象不会复制旧原始流、执行表和同步事件。消息入口复制到选定路径为止，通常比复制整张分支图更轻。复制及恢复有自己的消息／备份检查，后续发送仍受历史和数据库保护，不能承诺一定恢复可继续状态。
- 原对话可先导出备份。删除不需要的消息可能减少净内容，但仍保留分支连接、删除标记和必要幂等记录，不能当作可靠的数据库压实按钮；不自动删除旧分支。
- 仅改变模型、减少发送给模型的条数或创建历史摘要，无法直接解除这条物理数据库保护；升级 Workers 套餐也不会自动改变代码中的 16 MiB 判断。

## 修复原则

以状态恢复取代通知历史回放，先减少重复数据和错误拒绝，再扩大容量。继续使用现有低频持久化与客户端高频显示，不加应用每日用量限制、不换套餐、不引入新收费存储来绕开问题。

客户端可以继续高频解析原始预览，服务端必须独立形成可信检查点，不能要求客户端在线或信任客户端上报的正文才能正确保存。解析放在 DO 的有界批次处理路径，SQL 仍低频提交；不能因删除日志而改成每 Token 写入，也不能在每个检查点重新解析从头到尾的完整流。

完整累计正文在每个检查点反复覆盖也会产生写入放大。目标将已完成的正文／思考片段追加为规范内容块，仅更新有界尾块和解析状态；不再同时保存「内容块 + 同内容的完整正文 + 完整原始流」。分块大小、提交间隔和 CPU 成本用原生测量决定。

单对话预算不能代表账户剩余空间。旧策略的 128 × 32 MiB 已约为 4.295 GB，接近 5 GB 总额，还没算 Library、搜索及其他部署；不能直接把每对话改为 1 GB 并宣称仍受免费层兜底。

Cloudflare Free 的 DO SQLite 当前为每日 500 万行读、10 万行写；DELETE 也计写入。统计和维护必须按需、批量执行，不能在每个 Token 或每次预览上扫描全库或做清理。[DO 定价](https://developers.cloudflare.com/durable-objects/platform/pricing/)

## 实施顺序

### 1. 明确原因与只读统计

- 给错误增加稳定代码及阶段：准入预算、流写入预算、终态预算、历史快照过大、平台存储不足；不只让前端判断中文字符串。
- 在鉴权接口按需提供 `databaseBytes`、消息及版本数量、正文／思考／工具结果净字节、现有 `events` 行数与负载字节、公开／私有流字节、请求指纹字节、仍保留的上下文字节、任务状态。只返回计数，不返回正文或密钥；事件表移除后不为诊断继续保留该表。
- 使用可重复的合成长流与多版本数据，测量生成中峰值、完成后、清理后及重新实例化后的差异。验证可用的 SQLite 页统计；不预设 DO 支持 `VACUUM`、任意 PRAGMA 或本地 SQLite 的维护方式。
- 记录是否为「数据仍多」或「冗余／分配高水位」，避免建议用户反复删除正文却无法恢复。

### 2. 用当前状态同步替换持久化事件

- 新增独立的对话 `revision`／重置代次 `epoch`，消息和删除标记保存各自最新修改版本；设置等同步状态也有对应修改版本。修改权威状态和推进版本号在同一事务中完成。
- 新客户端通过订阅握手获得基线并开始接收后续变化。注册订阅、确定基线版本和接入在线尾部之间不得有未处理的并发缺口；GET 可用于预加载，不能再依赖一份永久事件历史补救 GET／订阅竞态。
- 重连比较客户端与服务端版本。相同时直接就绪；不同时，按 `updatedRevision` 读取变化对象的**最新状态**和删除标记，或重新获取基线。相同消息发生多次变化也只保留当前状态，不保存所有中间通知。同步包携带起止版本，不再要求每个历史事件序号连续。
- 在线仍可发送正文增量、原始预览和持久化确认；这些包不写事件表。缺包、旧缓存、DO 重启或代次失配时，重新取得该消息的检查点或对话基线，不要求重放自生成开始的所有原始字节。
- 为避免提交完成但广播丢失后永久不一致，在握手、恢复前台及低频存活校验时比较权威版本；该检查不产生周期性 SQL 写入。慢客户端仍使用有界窗口，落后过多则重新同步。
- 删除标记必须覆盖可能重连的旧客户端；若回收标记，推进重置代次并要求旧缓存完整替换，不能只按时间删除后继续合并旧缓存。
- `submissions` 改为保存规范输入的 SHA-256 及结果引用，包含手动编辑路径。既有请求记录一次性转换时保留其结果与去重语义。
- 新协议和持久化版本可靠生效后移除旧 `events` 数据、schema、回放分支及依赖它的测试。保留对用户功能、收敛和故障恢复有意义的测试。

该阶段可以暂时保留**单份、仅活跃期间存在的** `stream_commits`，让现有服务端物化路径继续生成可靠快照；这不再是另一个公开同步事件库。仅移除事件表已能消除完成消息的主要放大来源，公共原始流的生成中峰值在下一阶段继续处理。

### 3. 生成过程持久化为检查点和规范内容

- 服务端低频处理新增原始字节，追加规范正文／思考内容块，并原子保存同一边界的 `runId`、可靠偏移、解析状态、消息状态和持久化版本；事务可靠完成后才确认对应预览已保存。
- 新客户端在生成中加入时，读取最新可靠前缀和解析检查点，再接入内存中的有界未提交尾部。偏移必须按运行 ID 校验，旧运行、重复批次和越界尾部不能拼接到新回答。
- 原始公开流在已消费并形成可靠检查点后即可丢弃；最终不再需要随回答长度增长的 `stream_commits`。原始预览传输也不要求沿用数据库中的 Base64 文本表示。
- 正常完成、取消、供应商失败和超限均以最后可靠检查点形成终态；掉电／实例重启不能伪造完整回答，也不能自动重发已认领但结果未知的模型请求。
- 工具私有日志先保持单份和现有短生命周期。当前 SDK 收集器会在流结束后读取它，只有改造成等价的增量结构化采集后才能进一步移除；签名、加密资料和工具调用顺序必须完整保留到下一轮不再需要时。
- 完成后清理解析临时资料、任务完整上下文和不再需要的私有续接；业务版本、工具来源和小型幂等依据继续保存。跨组件任务待办按成功确认回收，不能用可丢弃的 WebSocket 推送替代。

### 4. 分页、容量准入和已有对象整理

- 消息正文、分支元数据及历史分页分离；新客户端先获取小型基线和当前路径所需内容，未展示分支按需读取。模型上下文按父链构建；搜索定位、复制和备份也使用有界批次。
- 正文分页携带消息版本和基线版本，基线后的变化继续按最新状态补齐；读取期间版本不匹配就重取受影响消息，不能把跨请求的所有页面假定为同一 SQLite 事务快照。大内容不塞入单个 WebSocket 帧或巨型 JSON。
- 删除旧事件后，原数据库的物理分配不保证立即缩小。不再仅凭 `databaseSize > 16 MiB` 判定对话永久不可继续；准入结合有效数据、可复用空间（须原生验证）、本次输入／上下文及终态所需余量，覆盖普通聊天、修订、摘要和工具。
- 继续满足 SQL 单行边界，基于新架构的实际峰值重新确定预算；不能只删除 4 MiB 检查并继续全量拼接所有分支，也不直接把单对话阈值改为 1 GB。
- 对已膨胀对象优先验证空间重用；必要时提供显式整理方案，保证旧 URL、分支和引用关系。底层对象迁移需要写入冻结及引用处理，不假设 DO 支持本地 SQLite 的任意压实命令。
- 平台真正拒绝写入时仍保留可信前缀，不自动重发模型请求；单次任务时间、背压和失败保存空间继续受控。
- 账户用量采用 Cloudflare 监控与有动作的告警；按需聚合应用诊断，不构建新的高频账户扫描。5 GB 是账户所有对象共享的容量，不承诺由一个应用掌握全部剩余额度。

## 验收目标

1. 合成长协议／小正文、多轮修订和联网工具能够复现旧保护，统计明确指出主要占用；不使用私人对话作测试夹具。
2. 在低于有效数据预算且有足够可用空间时，超过旧 16 MiB 的对象可以继续对话；确实没有余量则在发起付费请求前拒绝。
3. 不存在持久化的公开同步事件历史；完成后的存储主要由唯一业务内容、必要元数据和幂等引用组成，不能随 SSE 帧数成比例膨胀。
4. 全新客户端不带任何旧事件或缓存，仍可恢复全部消息版本、分支关系、设置，以及正在生成的可靠前缀；生成中加入和「取得基线后立刻发生变更」均不漏消息。
5. 停止、断网、DO 重置、提交完成后广播失败、事务失败、平台配额错误均保留可信前缀；任务重入不重复调用供应商，旧分支和手动版本不丢失。
6. 旧缓存、未来版本、旧运行尾部、缺包、重复包、删除后的重连及代次重置都通过状态同步正确收敛；工具私有资料不暴露给客户端。
7. 长对话分页后，首次打开、切换版本及继续生成不再全量解析所有正文；复制、备份、搜索、删除、附件引用及跨设备同步正确。
8. 记录 SQL 行读写、数据库峰值、CPU 和重连传输量；预览不写库，持久化仍为有界批量操作，不在每个检查点重解析整个原始流或反复重写全部累计正文。本地结果不能代替真实平台免费额度测量。

优先以第 1–2 阶段消除主要长期副本，再通过第 3 阶段限制生成中峰值；第 4 阶段解决长对话读取和已有对象的容量判断。[DeepSeek 联网适配](deepseek-web-tools-plan.md)复用同一套存储与执行保护。

## 实施结果（2026-10-18）

- 权威状态独立存 `seq/epoch`，每条消息只保留最新修改版本；`events` 及公开 `stream_commits` 已移除。旧对象在同一事务内转换，保留消息、分支、删除标记、去重结果及活跃生成的可靠前缀；不保留旧协议回放入口。
- 客户端使用分页基线和最新状态差分，握手弥补 GET 后的竞态。版本／代次失配及大差分走重新取基线，20 秒存活检查修复广播丢失。初始读取每页最多 32 条、约 1 MiB，单条大消息单独一页；页面不是跨请求事务快照，后续握手以第一页版本补齐期间变更。
- 普通公开流仅增量解析，规范正文／思考按 4,096 码元存 JSON 字符串块，只更新变化尾块。检查点保留未完成 SSE、UTF-8 及供应商解析状态；事务失败丢弃内存解析器，重试从可靠状态恢复。终态清除解析器、上下文和不再需要的私有资料。
- 工具私有日志仍为 SDK 收集器保留单份短期数据，不进入公开状态；工具循环、重启和取消沿用执行认领，不能凭重连自动重发付费请求。
- 提交请求先读取分支元数据，只加载选中父链及覆盖该路径的摘要；计数不加载正文。客户端当前仍会读完分页基线以支持已有全图分支切换、搜索和离线恢复，未实现所有隐藏分支的永久懒加载；因此消息数、单条文本和备份边界继续保留，不进一步扩大。
- 取消全部历史 JSON 4 MiB 拒绝；准入由 16 调整为 28 MiB，写流 30 MiB、终态 32 MiB。鉴权只读 `/storage` 返回分类净字节及分配信息，不返回内容或凭据。存储保护错误含稳定代码／阶段，平台 SQL 错误继续脱敏。
- 页统计在原生本地运行时不可用，不能将 `reusableBytes: null` 当作 0 或假设 `VACUUM` 可用。当前保守使用分配体积；对超过新准入线的旧高水位对象，显式复制／恢复比未经验证的原地压实可靠。自动保持旧 URL 的对象迁移仍属后续架构扩展，不在本次自动执行。

合成复现修复后的 10 版本回归保留全部规范内容，SQLite 小于 2 MiB，不再随 80,000 个 SSE 帧保留双份协议历史。原生 workerd 工具链测量见 [storage-state-tools-local.json](../measurements/storage-state-tools-local.json)，通知负载 0 字节，完成后公开检查点及私有原始日志均为 0；191＋32 行写入覆盖实际 Conversation／Library 操作。Node SQLite 页体积与原生本地统计分开记录，不据此承诺线上 CPU 或账户总配额。

回归覆盖跨 UTF-8／SSE 边界的冷恢复、事务回滚、旧表转换、版本跨越、删除后重连、生成中加入、预览确认、慢订阅、容量失败、分支编辑、摘要、搜索、复制及备份。完整本轮验收记录见[执行结果](../measurements/plan-execution-2026-10-18.md)。
