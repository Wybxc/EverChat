# Durable Objects 空闲读取修复计划

日期：2026-11-01。状态：业务修复与本地验证完成，生产离线升级、发布与平台验收待执行。属于[同步与免费层资源排查](sync-worker-resource-investigation-plan.md)的优先专项，不重复计为独立开发目标。

目标是让空闲成本主要随连接数和必要鉴权重验增长，避免随对话数、历史消息数和十秒轮询次数相乘。保留跨端及时同步、任务恢复及 Workers Free 约束，不增加应用内对话／消息数量限额。

## 已确认的问题

[实验记录](../measurements/sync-idle-reads-2026-11-01.md)及原始报告给出以下证据：

- 生产上一额度周期 Library 占约 83% 读取；北京时间 02:00～03:00 读取 436,400 行，零写入、零 Alarm、372 次成功 jsrpc。聚合口径不能定位设备或单个方法。
- `useLibraryIndex` 每十秒请求完整列表；225 条合成对话每次读取 1,351 行，1,000 条时为 6,001 行。删除游标不减少列表读取。
- 可见但失焦时 TanStack Query 仍轮询，请求失败后 interval 也继续。仅设置 `retry:false` 或延长间隔不足以消除问题。
- Conversation 冷启动恢复查询扫描历史 runs；1,000 条终态消息读取 2,088 行。候选待处理消息索引使之降至 91 行，另有 1 行构造写入。
- 客户端每二十秒发送 `sync-check`，即使未变更也读状态；`session-check` 热处理无 SQL，但可能唤醒对象。当前最多五分钟 Access 重验后的重连还会先拉完整快照。

## 采用的同步方案

### Library：变更通知与当前状态

持久保存一条 `library_state(id, epoch, revision)`。`epoch` 区分数据库重建／恢复，`revision` 为安全整数单调递增；不以时间戳代替顺序，不建立可无限增长的同步事件表。备份恢复时由离线工具生成新的 epoch，避免旧客户端把恢复后的较小修订号误当成已同步。

所有影响列表返回值的业务变更，通过七张业务表的 SQL trigger 在写入的同一事务中递增 revision；只观察影响列表的字段，lease 续期和无变化的 UPDATE 不增加版本。事务提交后通过现有 Library 通知 WebSocket 发送 `library-changed {epoch, revision}`，通知不携带全文、不随生成 Token 推送。复用在线连接与平台 ping/pong 自动响应，不新增第二条 Library 长连接，也不要求用户开启系统通知。

从通知控制器抽出可复用的认证连接生命周期与订阅分发，通知展示仍归通知模块。现有连接在没有通知权限时也会建立；保留完成通知的焦点探测与跨设备抑制逻辑。Library 变更广播独立于通知设备枚举，不能每次为广播遍历查询全部订阅数据库。

客户端存储最后应用的 epoch／revision 及列表。连接建立／重连时获取当前水位：相同则不读取全量；不同则合并触发一次当前快照获取。首期采用“有变化才获取完整快照”，不同时增加按条目增量协议。后续仅在活跃负载测量证明必要时，再比较逐条增量和分页方案。

列表、activity、删除游标和已应用水位作为一致缓存快照持久化，不能先保存新 revision 再保存旧列表。缓存缺失、写入失败或所属身份改变时按首次加载处理，不能仅凭保存过的水位跳过恢复。

### 必须处理的竞态

1. 先注册订阅，再发送 ready 水位；基线读取与订阅登记之间不允许漏掉事务后的通知。发送前重新检查授权租期。
2. 完整快照的数据与返回的水位必须在同一同步事务／无异步间隙内获取，禁止把旧列表配上新 revision。
3. 客户端保存“已应用”和“已观察到的最高 revision”。GET 进行时再收到通知，完成后若最高水位仍更新则追加一次获取；乱序响应不能覆盖新状态。
4. 首次 GET、连接打开和焦点恢复可能同时触发；按 owner／epoch 合并请求，取消旧身份的响应。断线／页面冻结后立即重新比较水位。
5. 删除继续使用已有 tombstone 和游标。多页删除记录不能每一页都重读完整列表；使用专门删除页或只在首个一致快照附带列表。分页过程中有新变更则补读至最新水位。
6. 通知发送失败不回滚已提交业务；连接断开后靠水位补齐。对持续连接上的异常控制包应标记失步并重连核对，不能静默丢弃。WebSocket 有序可靠传输之外不假设通知永久可用。

必须逐项审计修订号更新入口：新建、标题修改、置顶、删除及删除完成清理、复制／导入的接受与完成／失败、自动标题任务状态、activity 的排队／运行／停止／空闲转换。底层 store、Alarm 和恢复路径中的直接 SQL 也须覆盖。旧版本／重复 activity 报告及未改变可见状态的幂等调用，不应无意义增加 revision。

低频活动索引仍只保存最新状态和版本水位。修改当前 `activityFresh` 的二十五秒数据年龄判断：有有效租期且已追平 revision 的连接可以确认未变化的状态；断线／恢复中显示待同步。不能移除轮询后让全部正常生成状态二十五秒后自动失效。

### Conversation：减少唤醒与重复读取

- 新增与 `status IN ('queued','running')` 恢复查询匹配的部分索引。先保持查询和中断恢复语义，仅改变查询路径；不删除恢复逻辑，不自动重发已开始的供应商请求。
- 移除每二十秒的数据库 `sync-check`，平台 ping/pong 继续确认连接存活；连接恢复、回到前台或检测到序号缺口时比较当前状态。活跃生成仍走现有 preview／commit／ack 协议。
- 保留 Access JWT 验签、声明验证、对话权限检查、过期检查及最多五分钟重新授权。普通 ping 的自动响应不等于续期，过期连接不得继续收到业务数据。
- 把“重新授权／建立 WS”与“完整快照加载”拆开。本地已有可靠 epoch／seq 时先尝试状态增量；服务端返回 epoch 不符、缺口或 baseline 无效才读取快照。首次访问仍正常读取完整状态，不能把本地预览当成已持久基线。
- 序号确认、租期和身份都保存在可休眠恢复的连接附件／规范持久状态中；内存缓存只用于加速。服务端不为每条空闲连接新增高频 Alarm。

Library 复用通道时同时明确授权租期：继承现有会话到期边界，使用与 Conversation 一致的最多五分钟重验策略。重验通过正常认证入口重新建立连接，不能复用未经重新验证的旧 JWT 结论。前后台恢复可合并重验，不让 focus 事件触发设备配置重复写入和完整列表读取。

### 页面生命周期和错误处理

页面 hidden／冻结时暂停主动同步及重连；恢复可见且在线时立即检查水位和当前对话。可见但失焦／长期闲置时不轮询，但仍可被动接收低频变更；不能只依据 visibility 假设用户正在操作。后台通知继续由现有 Web Push 管线工作，不靠保活页面。

明确识别上游平台配额错误与一般临时故障；平台未提供稳定错误码时如实归类为服务不可用，不仅凭所有 500 就宣称额度耗尽。连续失败进入带随机抖动的退避，停止密集 interval 和快速重连，保留本地列表／草稿／已保存内容；只有明确认证失败才触发登录。恢复网络、用户主动重试或退避到期再探测，成功后恢复订阅。不得为了绕过配额创建更多对象、清空对话或降低持久化可靠性。

## 数据库升级与发布

生产 Library／Conversation 当前为 schema 6；本次代码将 `STORAGE_SCHEMA_VERSION` 升至 **7**。离线工具已加入 Library state／trigger 和 Conversation pending 索引；必须覆盖全部 Library／Conversation 对象，包括已删除对象。UsageStore 和 ShareStore 使用各自版本，不随本次变动。备份／补丁／verify 包含新表、索引、trigger，以及原有 activity、标题与预留记录，不能只改在线 schema 声明。

沿用[离线运维流程](../operations/offline-storage-migration.md)：结束活跃任务，维护窗口内导出，**本地**初始化单行状态和建立索引，生成补丁，再写回逐对象校验。构造函数只创建空库和校验版本，不回填历史、不在线建旧数据索引。运维工具要覆盖删除对象、复制／导入引用及重复执行，保留对话 ID、分支、运行记录、附件和幂等结果。

先准备可审查 PR 并通过必需检查，再执行维护窗口、核验并合并发布。回滚须先恢复相匹配的数据库备份，再恢复业务版本；不能仅回滚代码导致 schema 拒绝启动。不新增运行时旧协议双写／兼容迁移。若要创建云端隔离资源或新凭据，另按实际范围取得授权；本轮实验没有使用这些资源。

## 验收目标

以下是后续实施的目标，**不是本轮实验已达成的生产结果**。

1. 稳定、无变更时无定时完整列表 GET，无二十秒数据库 `sync-check`；列表从 225 增至 1,000 条，空闲周期不增加全量扫描。首次基线读取单独列出。
2. 全部历史消息终态时，0／20／200／1,000 消息的本地冷构造读取维持近似常量，候选参考值 91 行，初始回归门槛不超过 120 行；新增功能改变固定开销时必须说明差异。原生建索引成本和活跃任务恢复另外测量。
3. 三个在线客户端、1,000 个对话、当前对话 1,000 条终态消息、24 小时无业务变更且保留最多五分钟鉴权重验，**稳定空闲总读取目标不超过 25 万行／日**。先用实际路径短窗计数建模，列出首次加载与重连额外成本，再用获授权平台窗口核对；不可把“单行 revision 查询”当成整次请求成本。
4. 正常在线时跨端新增／改名／置顶／删除／生成生命周期目标两秒内可见；突发通知合并获取，连接重建与遗漏通知测试最终一致。活跃变更下的列表开销单独报告，若频繁全量仍过高再决定按条目增量。
5. 权限撤回／到期后无业务数据泄露；后台通知、焦点抑制、自动标题、取消、复制／导入、离线草稿与流式恢复无回归。配额异常不触发持续高频探测或清空本地状态。
6. 同口径报告 rows_read、rows_written、请求、活跃时长、CPU、存储与失败。原生计数不等于平台账单；不能承诺所有生成量、客户端数量和业务负载都在免费层以内。

既有 CPU p99 尖峰、10393 和 DO 指标缺项仍由上级资源排查跟进。本专项完成的条件是实现、离线升级与上述验收均有证据，不能仅凭本地候选查询通过就关闭问题。

## 本地实施结果

- 阶段 1～3 已完成。列表使用原有通知连接上的 ready 水位／变更包，移除十秒全量轮询；删除分页只读取一次列表。列表、活动、水位和删除游标统一保存为一个缓存值。
- Conversation 不再发送定时数据库检查；可靠 epoch／seq 缓存优先增量恢复。两类连接均保留最长五分钟的重新鉴权，hidden／offline 暂停，持续失败指数退避至五分钟。仅收到 ready 不重置失败计数，避免快速断开造成重连风暴。
- 通知权限、焦点抑制及后台 Web Push 保留，已同步的设备设置不因恢复焦点重复写入。清理了不再使用的 `reconnecting-websocket` 依赖。
- 6 → 7 离线补丁可回放，旧库启动拒绝且不改变数据；回滚先在本机生成并保存新的同步 epoch，再恢复与逐行核验。请求路径不运行旧数据迁移。
- [修复后原生报告](../measurements/sync-idle-reads-after-2026-11-01.json)中，0／20／200／1,000 条终态消息的冷构造均读取 **91 行**；Library 冷构造固定 116 行。真实内部升级处理器的热读数：Library 控制连接 1 行、对话访问检查 3 行、Conversation 同步握手 1 行。JWT、路由、平台休眠和网络不在这些内部计数内。
- 本地浏览器已验证无空闲轮询、双连接续期不重拉全文／不写设置、GET 与通知竞态、后台恢复、快速断线退避、复制和 Access；通知 PWA 回归通过。具体数量和局限见[实现与复测记录](../measurements/sync-idle-reads-after-2026-11-01.md)。

没有执行生产迁移或发布。25 万行／日仍是待核对目标：若每轮续期合并 Library 冷启动，三客户端合成模型约 18.3 万行；若控制连接与会话授权分别造成 Library 冷启动，则约 28.3 万行。二者均非平台实测，不能选择较低值宣称验收通过；首次加载、生成、业务变更和其他请求另计。
