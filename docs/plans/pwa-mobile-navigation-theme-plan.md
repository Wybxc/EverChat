## 2. PWA：先定位失败阶段，再决定修复

### 2.1 当前问题

根因不是单一的错误文案，而是三个环节相连：

1. `wrangler.jsonc` 未显式设置 `assets.html_handling`，Cloudflare 默认采用 `auto-trailing-slash`，把预缓存清单中的 `/index.html` 307 重定向至 `/`。真实已登录 macOS PWA 的网络记录确认了该行为。
2. `src/sw.ts` 的 `fetchDidSucceed` 拒绝所有 `response.redirected`，因此正常的同源 HTML 规范化重定向也会让首次预缓存安装失败。浏览器移除没有 active worker 的注册。
3. `src/platform/pwa/controller.ts` 仍保留原先的 `registration` 引用。再次 `registration.update()` 时 Safari 抛出 `InvalidStateError: newestWorker is null`，被 catch 统一转换成“更新检查失败，请恢复连接后重试”。后台恢复可见、重新联网也能进入此路径。

同一份本地生产构建，在隔离的真实 Cloudflare 静态资源运行时做了对照：

| 配置                           | 首页预缓存                | 安装后的注册        | 后续更新            |
| ------------------------------ | ------------------------- | ------------------- | ------------------- |
| 生产默认 `auto-trailing-slash` | 307 后 `redirected: true` | 0，无 active worker | `InvalidStateError` |
| 仅改为 `html_handling: none`   | 原路径 200，无重定向      | 1，有 active worker | 成功                |

对照使用 Chromium；线上原始异常来自真实 macOS Safari PWA，两者不是同一条浏览器错误文案。iOS 尚未接入远程检查器，不能声称已取得 iOS 独立请求证据。当前是跨平台的配置与生命周期缺陷，不需要预设 Safari 特有 Cookie 缺陷。[Cloudflare HTML handling](https://developers.cloudflare.com/workers/static-assets/routing/advanced/html-handling/)。

此前只让 `/sw.js` 返回 503 的夹具仅证明文案会误导，不能定位此次根因。既有 PWA 测试使用自行实现的 Node 静态服务器，未复刻 Cloudflare 的 HTML URL 规范化行为，因此漏掉了这条安装失败链。

实际需要区分：脚本检查失败、认证重定向、脚本 MIME 不正确、脚本成功但离线资源安装失败，以及等待新版本激活。这些并非同一种故障。

Access 过期仍需另行覆盖：SW 顶层脚本请求的重定向模式为 `error`，不能跟随登录跳转。修复 HTML 路由后仍应验证过期、重新登录和重试；不要把匿名 302 当作本次已登录故障的证据。[Service Workers 更新算法](https://w3c.github.io/ServiceWorker/#update-algorithm)、[Cloudflare Access 认证 Cookie](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/)。

### 2.2 补齐有边界的诊断

为 PWA 控制器保存最近一次操作的结构化结果：操作来源（手动／后台）、阶段、时间、页面版本、SW 版本、错误分类和脱敏摘要。默认界面只展示必要操作；设置内可展开或复制诊断。

- 记录注册、检查脚本、安装资源、等待更新、协调刷新各阶段。保留现有多标签草稿保护。
- 原始异常只能作为诊断线索，不能凭 `TypeError` 就断定断网或登录失效。
- 手动失败时按需检查同源会话与脚本响应。使用明确的凭据与缓存策略；若使用 `redirect: 'manual'`，跨源重定向可能只得到 `opaqueredirect`，不能假定能读取目标地址或状态码。
- 只有明确的会话验证失败才能提示重新登录；会话有效但 SW 请求异常时保留“不确定”分类，继续核对独立 PWA 的实际网络请求。
- 不记录 Cookie、JWT、密钥、完整请求正文或带登录参数的 URL；不因诊断额外上传遥测。
- 复用已有会话刷新与单次诊断，不在每次可见性变化时探测所有静态资源。必要时在现有会话响应中附带发布构建标识，避免增加轮询端点。

真机采集至少包含：系统／Safari 版本、standalone 状态、页面和 SW 版本、`/sw.js` 的状态／MIME／重定向情况、是否发送认证 Cookie（只记有无）、会话验证结果。iOS 与 macOS 分别采集，不能假定两个应用共享认证状态。

### 2.3 用户行为与错误反馈

| 状态             | 交互方案                                                                                 |
| ---------------- | ---------------------------------------------------------------------------------------- |
| 明确离线         | 保留可读内容；后台检查安静跳过，手动检查提示“当前离线，联网后重试”。                     |
| 已证实登录失效   | 提示“登录已失效，重新登录后检查更新”，复用现有登录流程；保留对话 URL、草稿和待发送请求。 |
| 503 等服务异常   | 提示“更新服务暂不可用，请稍后重试”，提供重试。                                           |
| MIME／脚本异常   | 提示“更新文件异常，请稍后重试”，详情给出阶段；不把登录 HTML 写入静态缓存。               |
| 原因尚不确定     | 提示“暂时无法检查更新，请重试”；不误指向断网、额度或浏览器损坏。                         |
| 资源下载中／失败 | 独立显示安装阶段，可重试；保持原 SW 和当前页面可用。                                     |
| 新版本已就绪     | 沿用“更新／稍后”和多标签页准备流程。                                                     |

后台瞬时失败在设置中保留状态，避免每次切回 PWA 都弹全局错误；手动操作失败要有明确反馈。后台检查合并执行并退避，恢复联网后允许重试。

为检查增加界面等待期限，初始建议 15 秒。`registration.update()` 没有 AbortSignal，超时只结束本次界面等待，不能宣称取消了浏览器更新任务；迟到结果由操作标识和 SW 生命周期观察器协调，避免旧错误覆盖新版本就绪状态或连续排队检查。

### 2.4 架构决策与安全边界

按已定位的根因实施：

1. 首选在 `wrangler.jsonc` 显式设置 `assets.html_handling: 'none'`，让预缓存的 `/index.html` 直接返回 200。保留 SPA fallback；核验 `/`、对话深链接和带版本查询参数的首页。该选择已通过本地平台对照，不需要允许任意重定向。如果之后保留 HTML 规范化，则必须同步把预缓存首页和导航 fallback 改为规范路径，不能只改其中一处。
2. 安装进入 `redundant` 且没有 active／waiting worker 时，清除失效注册引用。手动重试先重新获取或注册当前 scope，再更新；对 `InvalidStateError` 只进行有界的重新注册，不循环重试，也不删除业务存储。
3. 保留原始异常类别与阶段，替换 catch-all 连接文案；将“资源安装失败”和“检查脚本失败”分开。完整体验调整见 2.2、2.3。
4. 增加实际 Cloudflare 静态资源运行时回归，覆盖默认重定向导致安装失败、随后旧引用更新失败，以及修复配置后初次安装与重试恢复。Node 故障夹具继续覆盖 503 等情形，不能单独承担部署语义验证。
5. 实施后在 macOS 与 iOS 已安装 PWA 分别验证首次安装、检查更新、重新打开及 Access 失效恢复。先确认此次故障消失，再归档真机证据。

保留现有全站 Access 和拒绝认证跳转的预缓存保护，不通过清空 IndexedDB、强制注销所有 SW 或放宽认证来掩盖问题。

如果真机证明确实需要将静态应用壳与访问控制拆开，再单独评估同源、严格限定路径的静态资源发布方式。必须明确公开资源清单，并持续保护 `/api/*`、附件与所有私有内容；这会改变原全站访问边界，应形成具体方案后取得授权。本轮不执行此类配置变更，也不将其预设为必要修复。

现有预缓存包含较多离线依赖。它会影响资源安装阶段，不能仅凭体积解释 `registration.update()` 的拒绝。后续用户明确要求缩小必需预缓存，将公式、PDF、字体等改为使用后缓存，实施记录见 9.5；不再承诺这些模块首次使用即可离线。

涉及模块：`src/platform/pwa/controller.ts`、`PwaControls.tsx`、`src/sw.ts`、会话恢复，以及生产 PWA 测试夹具。

## 3. 搜索：改为有边界的弹窗

### 3.1 布局与共享方式

复用设置窗口的 Modal、遮罩、固定标题区和内部滚动规则，提取必要的共享布局样式，保留各自业务内容。不要把搜索塞进设置的 Tab，也不要再为搜索维护全屏定位覆盖。

- 桌面建议最大宽度 `48rem`、最大高度 `min(42rem, 88dvh)`，居中显示；保留紧凑搜索框与结果密度。
- 手机保留至少 `0.75rem` 外部间距，并与安全区取较大值。用户这次要求的是弹出窗口，因此不直接继承设置目前在小屏上的全屏覆盖。
- 标题／关闭区与结果滚动区分开。搜索框与关闭按钮保持在上方；取消“对话／归档”切换，不另加“全部对话”筛选行。只有结果区滚动，并使用 `min-height: 0`。
- 关闭按钮放在弹窗标题区，移出 cmdk 的选项与按键作用域。保留可访问名称和至少 `max(2.75rem, 44px)` 的触控面积。
- 标题／正文／思考搜索覆盖全部未删除对话，包括原来已归档的对话。保留分页、离线反馈、真实链接和分支定位；只有选择结果才修改 URL。

### 3.2 关闭失败的定位与修复

目前没有证据支持单纯提高 `z-index`。先在失败设备上记录关闭按钮矩形、`elementFromPoint()` 命中、计算后的 `pointer-events`、遮罩／Sheet 存活状态、安全区和 VisualViewport 数据。

按证据处理：

1. 按钮落入系统安全区：让弹窗整体位于安全区内，不只移动图标。
2. 键盘导致视觉视口缩小或偏移：先使用 CSS 布局；真机仍不满足时，通过小型共享视口适配层监听 VisualViewport 的 resize／scroll，约束弹窗可见高度与位置，避免多处各算一套。
3. 关闭中的 Sheet 或遮罩截获触摸：协调“关闭侧栏 → 打开搜索”的生命周期，避免两个焦点陷阱和点击拦截层重叠。
4. 按钮内触摸被上层行为吞掉：在正确的事件边界修复，不全局设置 `pointer-events: auto`，不使用强制点击作为验证通过条件。

VisualViewport 与布局视口在软键盘、缩放时可能不同，`100dvh` 不能代替真机验证。[VisualViewport](https://developer.mozilla.org/en-US/docs/Web/API/VisualViewport)。

关闭后回到可见触发入口；从手机侧栏进入时回到“打开对话列表”按钮。点击搜索结果后，旧弹窗的关闭动画不能抢回焦点。保留 `Mod+K` 再次聚焦搜索、Esc 关闭和 IME 保护。

现有快捷键测试主要以窗口尺寸与键盘 Enter 验证关闭，不能证明真机触控正常。新增触屏 tap、滚动后关闭、键盘显示时关闭及快速开关回归，并调整原“全屏矩形”断言。

涉及模块：`GlobalSearch.tsx`、`Modal.tsx`、`SettingsDialog.tsx`、`src/style.css`、`App.tsx` 的开关与焦点流程。

## 4. 手势：右滑打开，左滑关闭

### 4.1 交互范围

仅对移动布局启用触摸手势；桌面鼠标拖动和滚轮不参与。保留现有按钮、遮罩、Esc 与快捷键作为同等可用入口。

- **打开**：从左侧应用内部窄区向右滑。初始建议起点为距可见左边缘 16–40 CSS px，并考虑安全区；最外沿留给系统返回手势。
- **关闭**：侧栏打开时，在侧栏内向左滑；对输入控件、选择文本、菜单、横向滚动内容和其他弹窗不启动侧滑。
- 页面正文纵向滚动、代码／公式／表格横向滚动、长按、缩放与多指操作不能触发侧栏。不得在整个聊天区设置禁止触摸滚动的样式。
- iOS 系统边缘手势具有优先权；不承诺能够覆盖系统行为。真机出现冲突时调整应用内触发区，保留点击入口。

### 4.2 实现边界

先用独立的 `useSidebarSwipe` 与小型手势状态机实现，不为单个侧栏引入通用动画框架。Radix Sheet 继续负责焦点、遮罩与辅助技术语义；重点验证“关闭状态开始拖动、打开预览、完成／取消”能否与它协调。

1. Pointer Events 只接受单个触摸指针。初始移动约 12 CSS px 后判定方向，要求横向位移明显大于纵向位移，例如 `abs(dx) > 1.5 × abs(dy)`；纵向先成立即交还滚动。
2. 触发区和侧栏按需使用 `touch-action: pan-y pinch-zoom`，在手势开始前声明；不等 pointermove 后才更改。浏览器接管时正确处理 `pointercancel`。[touch-action](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/touch-action)。
3. 确认横向拖动后捕获指针，限制面板位移与遮罩透明度。用 ref／requestAnimationFrame 更新视觉进度，不逐帧写 React 业务状态或本地存储。
4. 初始完成阈值建议面板宽度的 25%；快速甩动可用约 0.5 CSS px/ms 的速度及至少 40 CSS px 位移辅助判定。数值必须在真机校准，不作为不可调整常量。
5. 已认定为拖动时只抑制本次落点的链接点击，防止关闭侧栏同时跳进对话；取消、多指、失去捕获、旋转和断点变化都要释放状态。
6. 打开预览、取消回弹和真正提交状态分开，避免未完成滑动就转移焦点或修改持久化状态。优先处理 Radix 的挂载／退出动画协调，不叠加两套竞争 transform。
7. 设置、搜索、图片预览、菜单或 PWA 更新准备期间不启动背景手势。尊重 reduced-motion，完成后才按现有规则恢复焦点。

若拖动预览需要修改 Sheet 原语，先完成一个最小验证；只有证明现有原语无法可靠配合后，才比较成熟手势库，不能通过复制另一套侧栏绕过问题。

## 5. 主题：选定“石榴莓”

保留当前中性背景、紧凑布局与组件形状，主色改为偏冷的石榴莓红。目标是摆脱当前 DeepSeek 蓝色的近似，同时避免直接采用常见蓝紫、青绿或陶土橙主色路线；不新增主题选择器或大面积渐变。

“不重复”以主要竞品的视觉区分为验收目标，不能承诺全球所有产品均未使用相同色值。上线前用相同浅深色场景与 DeepSeek、Claude、Qwen、Perplexity 做截图并排检查，关注整体识别而非仅比较一个十六进制值。[DeepSeek](https://www.deepseek.com/en/)、[Claude](https://claude.com/)、[Qwen](https://qwen.ai/)、[Perplexity 品牌色参考](https://live.standards.site/perplexity/color)。

### 6.3 数据与部署

沿用原型阶段直接调整契约的原则，不增加新旧 API 双写、归档兼容开关或长期双结构读取。

1. 新建数据库直接创建仅含 `id`、`pinned` 的 `conversation_metadata`。对已有数据库执行一次可重入的原子结构清理，事务中只复制 `id` 与 `pinned`，删除归档列；不重建对话表，也不删除任何对话或附件。结构清理失败时回滚，不继续使用半完成结构。
2. 取消客户端对归档的过滤后，已有本地缓存中的归档对话也应立即可见，不等待云端同步。正常同步将新的元数据形状写入缓存；无需清空 IndexedDB、草稿、待发送队列或会话数据。
3. 搜索分页范围变更时重新开始查询，清除本次搜索的旧页与旧游标，继续使用现有 revision 失效机制。归档只是查询过滤，现有全文索引不因此整库重建或重新读取全部消息。
4. 前后端与数据库清理在同一次发布中完成，先验证 PWA 更新路径再上线。本轮不增加旧客户端适配层；验收当前版本在刷新与离线恢复后均使用统一列表。

删除归档状态不应触发模型请求、取消生成、重新排队标题任务，或为所有对话逐条发起“取消归档”请求。

### 9.1 WebKit 补充排查

补跑 Playwright WebKit 27.2 时，发现旧缓存修复会使无关 CacheStorage 条目的内容消失。独立最小对照确认：相同页面普通刷新保留内容；只执行注销 SW 再刷新，即可重现无关条目内容丢失，缓存名仍在。此问题独立于此前首页重定向根因。

据此调整修复机制：由客户端使用带随机修复标识的脚本 URL 安装同一 scope 的新 worker，并为它建立独立应用缓存代次。下载成功后沿用多标签准备协议激活；激活时只清理其他旧应用静态缓存。不再注销 worker，也不先删除正在使用的缓存。相同应用版本的缓存修复仍协调刷新所有已准备页面；下载失败时原 worker 与原缓存保持可用。

该机制已通过正式配置中的全部 27 项双引擎 PWA 回归，包含无关缓存、草稿和待发送请求保留、下载失败保留原缓存，以及已存在等待更新时仍使用新修复缓存代次。WebKit 测试与 Chromium 测试分别重置设置夹具，避免前一引擎已保存的相同提示词导致“未保存”断言失去前提。自动化 WebKit 不代表已安装 Safari PWA 真机验收。

用户在独立 iOS PWA 发现搜索框获得焦点时页面自动放大。核对实现后确认：全局搜索与模型搜索共用的 `CommandInput` 使用 `text-sm`，默认实际字号为 14 CSS px；原触屏字号规则只覆盖普通 Input、Textarea 和 NativeSelect，遗漏 CommandInput。新增浏览器回归在修复前以「期望 16px、实际 14px」失败，证明了该样式遗漏。WebKit 的聚焦揭示流程将节点字号传给缩放计算，参见 [WKContentViewInteraction.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/ios/WKContentViewInteraction.mm)；尚未直接采集本次 iOS 的原生缩放比例，不把浏览器夹具当作真机复测。

沿用集中触屏样式，补入 CommandInput 和对话内搜索的原生输入框，字号使用 `max(1rem, 16px)`：保留用户增大字号的偏好，也在根字号偏小时保留 16 CSS px 下限。媒体条件调整为 `any-pointer: coarse`，覆盖同时提供触摸和精细指针的设备；桌面纯鼠标界面的紧凑字号保持原样。没有添加 `maximum-scale`、`user-scalable=no`、缩小 transform 或聚焦后强制复位缩放；手动缩放保持可用。

新增回归核对竖屏／横屏、12／16／20 CSS px 根字号下的全局搜索、模型搜索、对话内搜索、消息草稿及设置输入控件，检查实际字号与触摸焦点，并保护草稿和可缩放 viewport。生产 PWA 的移动关闭用例同时在 Chromium 与 WebKit 核对竖屏、横屏和缩小视口时的搜索字号，2 项通过。19 项相关 E2E 首轮 18 项通过；1 项滚动侧栏后左滑关闭失败，保留原断言与产品代码隔离补跑通过，未确定首轮失败原因，不写成已修复的手势缺陷或一次全绿结果。正式构建（含类型检查）、相关文件格式检查及差异检查通过。
