# EverChat MCP Server 设计

日期：2026-10-21。状态：核心实施完成，本地验收通过；生产发布待离线维护。本文设计的是让外部 AI 客户端操作 EverChat 的 MCP Server；现有联网工具不因此改为 MCP 客户端。生产 Access 配置尚未修改。

已确认范围：所有调用保存为正常对话，不增加临时调用模式和模型 JSON Schema 输出。MCP 接口本身仍使用结构化参数与结果契约。

## 产品定位与参考

用户明确的目标是“提供一个可以统一调用的自动化聊天接口”。因此核心交付围绕模型调用、上下文延续、可靠执行与结果获取设计，历史检索和工作区管理放到扩展阶段。

上层使用同一份输入与结果契约调用已配置的 OpenAI Chat Completions、Responses、Anthropic、Gemini 等协议，供应商适配与密钥由 EverChat 处理。底层形成统一聊天应用服务，MCP 是其工具适配层；后续 HTTP／SDK 可复用这份契约，但首版不同时承诺另一套 OpenAI 兼容代理 API。

## 首版四个核心工具

| 工具                   | 作用                                                                             |
| ---------------------- | -------------------------------------------------------------------------------- |
| `everchat_models_list` | 返回可调用模型的稳定引用、名称、供应商与能力，调用方配置一次即可复用             |
| `everchat_chat`        | 统一发起聊天；无续聊引用时自动新建并发送，有引用时沿指定位置继续；可短暂等待结果 |
| `everchat_run_get`     | 查询／等待同一次调用，按游标读取已保存的输出、终态、用量与错误；不会重新调用模型 |
| `everchat_run_cancel`  | 停止调用方有权操作的指定任务，返回实际确认状态                                   |

首次调用无需先创建空对话或列出历史。首版不注册单独的 create、send、regenerate 工具来增加常见调用步骤。需要从同一位置再次生成时，使用同一输入和续聊位置、配合新的 `requestId` 发起独立调用；旧结果保留。对已存在网页回答的原生“重新生成版本”操作留待历史管理扩展，不能与业务重试混为一谈。

## 统一调用契约

以下示例是工具 arguments 与业务返回值，不是供应商原始请求，也不是完整 MCP JSON-RPC 外层。

新建并提问：

```json
{
  "requestId": "b60fbbac-edcf-43c6-9bf1-d1f1881ab2d5",
  "modelRef": "configured-model-reference",
  "prompt": "请分析这份需求并列出实现步骤。"
}
```

完成后继续：

```json
{
  "requestId": "58141c29-555e-410c-9d01-a33ca5dceae2",
  "continuation": "opaque-conversation-position",
  "prompt": "把第二步展开。"
}
```

### 模型、提示词与参数

- `modelRef` 对应精确的供应商 ID 与模型 ID，调用方不传供应商 API 类型、端点或密钥。同名模型有不同引用；供应商显示名改变不改变模型身份。
- 首次调用显式指定模型；若配置自动化默认模型，可省略。该默认值独立于网页输入框的临时选择，未配置时明确报错。续聊未指定模型则继承该对话的服务器端配置，可显式覆盖，并在结果中回传实际模型。
- 统一选项覆盖预设／系统提示词、推理强度、Temperature／Top P、上下文与输出预算、网页搜索。首版保持精简可选字段，不暴露不同供应商的任意原始参数。
- `presetId` 和显式 `systemPrompt` 互斥；均未提供时按既有提示词配置解析。当前预设仅含名称与系统提示词，不将其误写为已有模型路由配置。
- 模型、提示词、工具及参数在任务接受时固定。未知能力沿用现有能力解析和实际请求诊断；明确不能满足的要求返回错误，不能静默忽略或擅自更换模型。
- 不做自动供应商故障切换、付费重试或隐式多模型调用。多模型比较由调用方并行发起独立请求，各自得到结果、用量和错误。

### 显式上下文与续聊位置

`continuation` 是精确定位到对话和父消息的引用，内部可封装 `conversationId` 与 `parentMessageId`，让普通调用方不必操作分支树。它不是授权令牌；服务端每次验证记录存在、当前可续聊状态和访问权限。

结果返回 `conversationId`、消息 ID、网页链接与下一次 `continuation`。只有可用回答才能给出可继续的位置；生成中需等待，已正式保留的中断回答可以按现有规则继续。只传会话 ID 不意味着“找整棵树最新的一条消息”，MCP 连接状态也不承担聊天上下文。

同一位置可显式发起多个独立分支。每个对话同时一个活跃生成的规则保持；忙碌时返回 `CONVERSATION_BUSY`，不静默排队或新建别的对话。客户端可创建独立对话实现并行调用。

### 统一结果

```json
{
  "status": "completed",
  "runRef": "opaque-run-reference",
  "conversationId": "conversation-id",
  "assistantMessageId": "assistant-message-id",
  "continuation": "opaque-conversation-position",
  "model": {
    "ref": "configured-model-reference",
    "providerName": "供应商名称",
    "id": "model-id"
  },
  "output": {
    "text": "分析结果……",
    "hasMore": false
  },
  "finishReason": "stop",
  "usage": {
    "inputTokens": 120,
    "outputTokens": 300,
    "isFinal": true
  },
  "url": "https://deployment.example/c/conversation-id?branch=assistant-message-id"
}
```

`runRef` 封装任务与所属对话的定位信息，查询工具不要求脚本拼装多个内部 ID，也无需为此新建全局任务索引数据库。网页链接方便人工检查；自动化依赖结构化字段，不从 Markdown 文案中提取状态。

结果使用 MCP 的 `structuredContent` 与 `outputSchema`，并按目标客户端需要附带文本表示；这些字段约束工具返回的状态、正文、用量等数据结构，模型回答保持普通文本。[MCP 工具规范](https://modelcontextprotocol.io/specification/latest/server/tools)

- 状态明确区分 `accepted`、`running`、`completed`、`interrupted`、`failed`、`cancelled`。供应商达到输出预算、过滤或断流不能全部伪装成正常 `stop`。
- 正文为默认输出；思考可显式请求。工具过程及来源的结构化返回留待扩展。长内容完整分页，提供游标和 `hasMore`；任务完成不等于当前页已包含全文。
- `everchat_run_get` 默认获取状态与已有结果，支持内容分页游标和有限等待。明确返回下一次读取位置，避免反复传输完整历史。
- 用量沿用现有可信记录；未知字段缺省或明确标记未知，不能补零。可返回当次费用估算及币种，不额外开放全部历史账单。
- 错误提供稳定 `code`、阶段、`retryable`、脱敏详情与结果是否未知。已有可靠部分输出同时保留，脚本不必通过异常字符串猜测发生了什么。

## 等待、重试与 Serverless 执行

### 快速完成直接返回，长任务继续获取

`everchat_chat` 在可靠接受任务后，可在调用方指定的 `waitMs` 内等待完成。短等待内完成就直接返回完整结果；到期则返回 `accepted/running` 和 `runRef`，后续 `everchat_run_get` 继续等待同一次任务。

建议首轮联调先提供 `waitMs: 0` 的确定性异步路径，再验证短等待默认值；目标为约 10 秒默认、约 20 秒单次等待上限，具体值通过目标宿主超时与免费层实测确定。这个等待窗口不截断后台生成，不改变现有任务期限，也不是输出长度限制。

MCP 请求断开或宿主取消一次等待不等于取消已接受的后台生成；只有 `everchat_run_cancel` 表达业务停止。等待逻辑放在适配层，不能把长 RPC 等待塞进 DO 并持续占用活跃时长。首版可低频查询，后续按实测复用现有通知路径，终态后停止。不能承诺所有 MCP 宿主都可将工具结果逐 Token 展示。

MCP Tasks 可作为能力协商后的增强，但首版普通工具返回的 `runRef` 是业务句柄，不冒充标准 Tasks 返回值。[Tasks 扩展](https://tasks.extensions.modelcontextprotocol.io/)要求客户端声明支持，不能作为所有自动化客户端都必须具备的前提。

### 幂等是首版能力

- `requestId` 是业务幂等键，与 MCP JSON-RPC 请求 ID 区分。自动化调用方必须稳定保存并在未知结果时复用；新 ID 表示主动发起新调用。
- 幂等记录按已验证调用身份隔离，并绑定规范化原始输入。同 ID／同输入返回原任务；同 ID／不同输入返回 `IDEMPOTENCY_CONFLICT`。
- 先找已接受请求，再读取当前模型／提示词配置；不能因配置已更新而将原请求重试当成另一次调用。
- 无 `continuation` 的新对话请求也必须可去重。由调用身份与请求 ID 稳定定位创建过程，记录创建、提交和 Library 登记的中间状态，不能重试一次就多建一个对话。
- 不宣称跨 Library／Conversation DO 的分布式原子事务。任务与输入在 Conversation 内事务提交，跨对象索引通过幂等步骤／现有 outbox 机制恢复，模型调用必须晚于任务可靠接受。
- 对供应商请求边界故障不能承诺外部“绝对只计费一次”；结果未知时明确标记并保留关联信息，不自动再次调用供应商。

## 保存策略与功能优先级

所有调用固定保存为正常对话：新建、续聊和结果在网页中可见，使用同一套聊天索引、搜索、分支、费用、中断保留与后台执行机制。接口无需存储模式参数，记录按现有正常对话规则保留与删除。不自动开启新对话通知策略，也不把 MCP 连接登记成网页前台焦点；通知仍按实际已配置规则处理。

按这一目标，后续顺序为：

1. 有限等待、断线恢复与长结果分页，完善自动化调用体验。
2. 按需支持调用方提供 `messages[]` 上下文。显式历史与 `continuation` 互斥，避免重复拼接上下文；输入历史也需按正常对话保存，并单独明确角色、提示词和附件语义。
3. 读取既有分支／预设，历史搜索与会话整理。
4. 分享、删除、Resources／Prompts 映射等按需增加。

供应商密钥管理、任意 HTTP／SQL／Shell、运维迁移及递归调用其他 MCP Server 不进入聊天工具。首版不增加模型别名路由、批量调度和自动故障切换；有实际需求再设计。

## 实现架构

```text
自动化脚本 / 外部 Agent
          │
      MCP 适配层
          │
      统一聊天应用服务 ── 后续 HTTP / SDK 可复用
          │
   Library / Conversation / UsageStore
          │
   既有 Alarm / WebToolWorkflow
          │
      模型供应商
```

使用无状态 Streamable HTTP 和官方 SDK，复用 [Workers／Hono 传输](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/packages/server/src/server/streamableHttp.examples.ts)，也可评估 Cloudflare [无状态 handler](https://developers.cloudflare.com/agents/model-context-protocol/apis/handler-api/)。不新建用于 MCP 会话的 DO、Workflow 或逐 Token 日志。协议依赖留在服务端，不进入前端包。

| 位置                                         | 改动                                                                                            |
| -------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `worker/mcp/`                                | 四个工具、参数／结果契约、认证上下文及协议装配                                                  |
| MCP 聊天应用服务                             | 编排模型／提示词解析、创建续聊、查询与取消，复用现有 HTTP 使用的 Library／Conversation 接收流程 |
| `worker/http/worker.ts`、`auth.ts`、`env.ts` | 路径分流，MCP Bearer Key 校验，保留网页 JWT 与同源保护                                          |
| Conversation／Library                        | 新建调用去重、任务引用、来源身份、有界结果读取及索引补偿                                        |
| `wrangler.jsonc`、部署文档                   | 协议入口优先进入 Worker，同源路径按需 Bypass；不硬编码个人域名                                  |
| 设置与测试                                   | MCP 密钥管理与权限说明；真实 DO 及 MCP 客户端闭环验收                                           |

MCP 不向自身 `/api/*` 发请求、不伪造 Origin 或 Cookie，也不绕过现有任务接受流程直接调用供应商。免费层采用既有资源政策；低频等待、分页和退避避免全文反复编码与读取，不为接口方便额外长期保存同步事件或结果副本。

## 鉴权：EverChat 可撤销 API Key

按照确认后的调整，MCP 使用 EverChat 自己签发的 Bearer API Key，不再依赖独立 Access 应用、AUD、Service Token 或 Managed OAuth。默认地址为网站同源的 `/mcp`，例如 `https://chat.wybxc.cc/mcp`；不需要新增域名。

### 签发与撤销

- 在受现有 Access 保护的「设置 → MCP」中创建、重命名、查看或删除密钥。桌面采用名称／脱敏 Key／创建日期／最近使用列表，手机采用紧凑列表；不显示 Tracking ID。最近使用时间最多每小时写入一次，降低查询场景的写入压力。
- 创建时用密码学安全随机数产生 256 bit secret，完整密钥仅在创建响应和当前设置面板中显示一次。关闭面板后不能再读取原值。
- 服务端仅保存 SHA-256 哈希、随机 ID、名称、脱敏提示、创建时间与低频使用时间；列表接口不返回哈希或 secret。前端缓存只保存列表元数据，不把密钥写入 localStorage、查询缓存或日志。
- 调用方使用 `Authorization: Bearer <key>`。不接受 URL query、Cookie 或工具参数中的密钥；不能将模型供应商的密钥用于 MCP 登录。
- 每次请求都验证密钥；撤销后立即拒绝后续调用。有限等待完成前再次检查撤销状态，不继续向已撤销凭据返回结果。已经接受的后台生成与普通对话保留；撤销凭据本身不等同于取消付费生成。
- 每个集成使用独立密钥。密钥 ID 就是业务来源身份，幂等、续聊、读取和取消均按这个身份隔离。新密钥不会自动取得旧密钥的历史任务权限，网页用户仍可查看这些普通对话。

### Access 路径边界

`/mcp` 必须在 Cloudflare 边缘允许到达 Worker，由 EverChat 的 API Key 验证授权。如果现有 Access 仅保护 `/api` 和 `/auth`，可以直接沿用；如果整站被 Access 覆盖，需要对**精确 `/mcp` 路径**配置 Bypass。不要放开 `/api/settings/mcp/keys`，这些管理接口继续使用网页 Access 身份与原有同源写保护。

API Key 只授予首版四个工具：模型发现、创建正常对话、继续该密钥自身任务的位置、读取和取消自身任务。它不能登录网页、读取供应商密钥或其他密钥／网页创建的历史，也不能执行 SQL、迁移、分享、删除等管理动作。全局模型允许列表可进一步限制可调用模型。

原生客户端无 Origin 时，凭据有效即可调用；浏览器提供 Origin 时严格检查网站同源。私有协议响应使用 `private, no-store`；SW 排除 `/mcp`，不返回 SPA 页面或离线缓存。未知／撤销密钥返回 401，跨来源返回 403，引用不能作为授权能力。

首版不提供 OAuth 授权发现；只支持 OAuth、无法配置请求头的客户端暂不在接入范围。需要标准交互授权时再单独增加，而不与本次 API Key 机制混合。

## 开发分期与验收

| 阶段          | 工作                                                               | 通过条件                                                                     |
| ------------- | ------------------------------------------------------------------ | ---------------------------------------------------------------------------- |
| 0：接入验证   | SDK 与 Bearer Key 联调，创建／撤销与路径隔离验证                   | 至少两种目标客户端可调用；脚本可无人值守，错误／撤销密钥被拒绝               |
| A：核心闭环   | 四个核心工具、统一输入输出、精确续聊、幂等、现有后台执行、异步取回 | 一次调用即可新建提问；不同协议返回统一结果；重复请求不新建任务或再次调用模型 |
| B：自动化体验 | 有限等待、断线恢复、长结果分页；全部保存为正常对话                 | 超时后取回同一任务；长结果可完整读取，正文与思考分别分页                     |
| C：工作区扩展 | 分支读取／预设、检索、整理及按需分享／删除                         | 每种能力独立授权，不扩大自动化调用凭据的默认权限                             |

核心场景验收：新建问答、多轮续聊、切换模型、不同模型并行、同对话忙碌、短等待直接完成、长等待超时、断线取回、业务请求 ID 重放／冲突、创建中间步骤失败、供应商中断与部分输出、取消、长正文分页、真实用量与未知结果。

安全回归：明文密钥不持久化、错误／撤销凭据、他人任务引用、未经授权的模型与历史、浏览器 Origin、MCP Key 不能访问网页 API、协议请求不进入 SPA／SW。协议与私有结果不进入公共缓存。

新增持久字段遵循离线运维迁移原则；不在用户请求或首次 MCP 连接中扫描和回填存量数据。已完成四个核心工具、可撤销密钥、管理页与离线迁移实现，已通过本地及两种客户端验收；尚未修改线上配置。
