# 回答「继续生成」计划

状态：实现与本地验收完成，等待 PR 检查及离线升级后发布。日期：2026-10-31。详见[验收记录](../measurements/answer-continuation-2026-10-31.md)。

## 目标与核心决定

用户可以对已有正文的中断回答点击「继续」，发起一次新的生成请求。新输出追加到原回答末尾，形成同一提问下的一个新回答版本。原回答及其已有后续消息保留在原分支。

**后续普通提问使用拼接后的回答作为一条 assistant 历史消息；实际执行过的「继续」请求和每次新增输出保留为可追溯的生成记录。** 两者分别承担对话内容与执行过程的职责，不将两套内容重复发送。

这是一种应用层续写。它不恢复之前的供应商连接，也不保证恢复模型先前的内部状态。模型可能重复内容、另起段落或改变措辞，产品不能保证任意模型都能逐字无缝续写。

## 上下文应该怎样发送

设 `H` 为较早历史，`U` 为原问题，`A0` 为中断回答，`D1`、`D2` 为两次续写的新输出。

第一次点击「继续」时，实际输入为：

```text
H
user: U
assistant: A0
user: 继续
```

模型生成 `D1`，新回答版本 `A1 = A0 + D1`。再次继续时发送：

```text
H
user: U
assistant: A1
user: 继续
```

下一次用户正常提问 `Q` 时发送：

```text
H
user: U
assistant: A1
user: Q
```

以上省略了系统提示、附件和固定材料；它们仍按统一上下文管理规则装配。控制消息使用字面文本「继续」，输入回执如实记录，不悄悄更换原问题或系统提示词。

采用这一方式有三个原因：后续上下文与界面中的回答一致；续写次数不改变普通聊天的轮次结构；模型更换、摘要和导出都能使用统一的回答正文。代价是普通上下文不会重放全部原始执行过程，因此必须提供真实过程记录，不能声称拼接结果由一次请求生成。

「逐次发送 `A0 → 继续 → D1 → 继续 → D2`」保留了执行顺序，但会让续写控制指令持续进入后续对话，也使显示内容和输入消息结构不同。本计划不增加两种可切换的历史模式；需要审计时读取执行过程，不改变普通聊天上下文。

## 与现有实现的衔接

- [`contextHistory()`](../../shared/conversation/context-budget.ts) 从选中分支的父链读取已完成消息，只将正文和附件组装为普通历史。续写版本应在这一入口被解析成完整正文。
- [`Conversation.submit()` / `finish()`](../../worker/conversation/durable-object.ts) 已支持新回答版本、请求幂等、低频持久化，以及部分供应商中断后保留正文。中断回答可能是 `completed` 并带有 `generation.interrupted`，不能仅通过 `failed` 判断能否续写。
- [`GenerationCheckpoints`](../../worker/streaming/checkpoints.ts) 已按消息分块保存正文和思考；当前块由消息 ID 持有，直接复制完整回答会重复保存前缀。
- [`Message`](../../shared/conversation/types.ts) 目前使用 `parentId` 和 `revisionOf` 表达分支，没有显式的续写来源与分段来源模型。
- [`InputReceipts`](../../worker/generation/input-receipts.ts) 的同次生成后续 round 用于工具续接。用户点击「继续」必须创建独立生成和输入回执，不复用工具 round。

## 分支与版本规则

```text
U
├─ A0：原中断回答 ─ Qold ─ Bold
├─ A1：A0 + D1
└─ A2：A1 + D2 ─ Qnew ─ Bnew
```

- `A1.parentId = U.id`，`A1.revisionOf = A0.id`，并记录明确的 `continuedFrom = A0.id`；`A2` 同理。
- 不把 `A1.parentId` 指向 `A0`，也不在正常时间线中插入隐藏的用户「继续」节点。
- 点击历史中间的回答继续，只产生新的兄弟回答；旧后续 `Qold/Bold` 留在原分支，不复制到新分支。
- 新分支沿用现有 `?branch=<messageId>` 导航与版本切换。提交成功后选中新版本；若用户期间已切换对话或分支，迟到响应不抢回页面。
- 手动编辑拼接回答仍走现有回答修订流程，生成独立的完整快照；标记来源为编辑，不伪装成模型的新输出。

## 交互与请求规则

| 情况                                               | 行为                                             |
| -------------------------------------------------- | ------------------------------------------------ |
| 供应商中断、输出长度结束、用户停止，且存在可靠正文 | 回答操作区显示「继续」                           |
| 回答正常结束，但用户仍希望扩写                     | 「更多」菜单提供「继续生成」                     |
| 正在排队、等待工具或生成中                         | 不发起续写；前端断网不等于服务端生成已结束       |
| 只有思考、没有正文，或来源已删除                   | 不提供正文续写，保留重新生成入口                 |
| 来源状态或内容尚未同步确认                         | 等待同步并由服务端校验，不基于客户端猜测创建版本 |

使用点击时聊天框选中的模型、思维强度、联网设置和对话参数，符合现有重新生成的配置方式。原问题的附件／固定材料使用对应分支的已固定版本；不发送尚未提交的聊天框草稿或草稿附件。

点击后立即展示来源前缀和生成状态，新内容在末尾流式出现。保留草稿和输入焦点，沿用现有滚动规则：用户在底部时跟随，上滚阅读时停止跟随，不因创建续写版本强制滚到底部。

服务端以 `continueOf` 作为独立提交动作，与 `retryOf`、`revisionOf`、`summaryThrough` 和普通消息内容互斥。复用 `requestId` 幂等，指纹包含来源 ID、已确认内容哈希及本次配置。同一请求重发返回同一版本，同一请求 ID 配不同参数返回冲突；双击和并发设备点击不能意外重复启动同一来源的续写。用户明确再次操作可以创建另一个版本。

## 内容存储：共享不可变前缀，新增输出单独保存

选择「逻辑完整回答、物理前缀引用加增量」作为实现方向。避免每次续写都在数据库中复制整个长回答。

概念结构如下，具体表名在实施时与现有 schema 对齐：

```text
续写关系：messageId、sourceMessageId、sourceTextSha256、sourceTextLength
本次执行：独立 runId、输入回执、控制消息、配置、用量、结束原因
本地正文：本次新增输出 Dn，使用现有分块存储和检查点
逻辑正文：来源版本的完整正文 + 本地正文
```

来源必须是已结束、不可变且已持久化的版本。`sourceTextLength` 明确使用 UTF-16 长度以匹配现有文本分页偏移；哈希使用规范 UTF-8 编码，空间预算继续按实际字节计算。引用和哈希在事务中固定，避免拿未落盘的客户端尾部作为前缀。

读取层提供统一的完整正文／分段来源解析器，供页面、上下文、搜索、分享、导出和 MCP 使用。流解析器与检查点只处理本次增量，其流偏移从零开始；显示位置另加前缀长度。不能将已拼接的 `Message.parts` 再喂给本次流解析器，导致前缀被重复写入或用量混淆。

多次续写的引用链在一次读取中批量解析并缓存，不能每个 token 都递归读取或展开整个链。正文分页游标绑定版本与逻辑偏移，能跨前缀／增量边界，保持 Unicode 正确。新持久化内容约为原文加各次增量及小量元数据；不为每个版本写一份完整前缀缓存。

删除旧版本只删除该版本的可见性，仍被其他版本继承的文本不会消失。物理内容的生命周期按存活引用管理；不能级联删除被新版本使用的正文、思考或工具结果。整个对话永久清除时统一回收。复制到新对话、备份恢复和分享快照必须自包含，不能依赖原对话仍存在。

这是对正文表示的明确扩展，实施时必须统一改造读取路径，不允许部分入口误把增量当作完整回答。schema 变更通过本地离线运维升级完成；不加入请求期间的格式探测、兼容回填或在线迁移。

## 上下文管理与真实输入回执

1. 从来源回答定位原问题及其分支，只收集该分支的历史。
2. 在既有摘要／材料／预算流程中，将原问题、来源完整正文和控制消息作为本次不可拆的末尾输入。来源即便是 `cancelled/failed`，只要有可靠正文且已经终止，也可作为这次显式续写的输入。
3. 可以按现有策略压缩更早历史；不得把待续写的原问题或来源正文悄悄截掉、摘要化后仍宣称完整续写。如果这一末尾输入无法容纳，提交前返回具体容量信息，由用户选择模型或调整上下文。
4. 输入回执准确记录来源版本、完整正文哈希、控制消息、实际保留／省略的历史、附件版本和 token 估计。普通后续提问的回执则记录拼接版本 ID，不冒充原来的多个物理请求。
5. 原回答的思考内容、供应商私有状态和未完成工具调用不作为伪造的助手历史重放。原工具结果保留为来源证据；新的工具调用仍由新请求正常执行。需要的材料依照现有显式输入规则纳入并在回执中体现。

不新增 SDK 之外的供应商续传协议，也不把用户续写与同一生成中的工具续接混为一谈。尤其不能将缺少配对结果的 tool call 或其他生成的签名直接接到新请求上。

## 拼接、思考与生成信息

- 正文严格使用 `prefix + delta`，不自动 `trim`、插入换行、删除相似句子或改写尾部。代码块、公式、列表可能正好在中断处未闭合，统一交给完整 Markdown 渲染；重复或语义冲突由用户编辑处理。
- 原始新增正文保留，不为视觉拼接改写存储。文档中的完整回答不插入会改变正文的「续写分割线」，来源入口放在生成信息中。
- 思考区默认折叠，内部按「原回答／续写 1／续写 2」保留供应商实际返回的思考与工具顺序。当前单一 reasoning 字符串和单个 tools 记录需要增加分段视图，不能直接拼字符串后丢失工具锚点。
- 工具调用与来源标识按生成 ID 隔离，显示偏移映射到对应分段；不同续写里相同的工具 call ID 不互相覆盖。正文中的自然语言引用不做模糊替换，不能自动保证模型重复的脚注编号语义正确。
- 生成信息区展示续写来源、次数、每次实际模型／供应商、时间和结束原因。相同模型维持紧凑标题；跨模型时以「多模型」等简短标识提示，并可查看每段来源，不能把整篇归给最后一个模型。
- 字数统计以拼接全文为准。用量／费用区分「本次请求」与「组成此版本的请求合计」；账本仍按实际执行入账一次，同一来源被多个版本引用不重复计费。新请求的输入 token 包含再次传入的前缀，这是实际供应商用量。
- 最新续写若再次以 `length` 或中断结束，保留明确状态并允许再次继续；不得因祖先曾中断而把已经正常结束的本次执行误报为失败。记录历史原因不等于证明最终正文在语义上完整。

## 失败、停止与恢复

- 提交被拒绝：不创建新回答，不改变当前分支或草稿。
- 接受后尚无新增正文就失败／取消：保留失败执行及其回执；前缀仅供参考，不把继承来的正文当成本次成功生成。若页面仍停在本次尝试，恢复来源版本作为后续聊天起点，失败尝试仍可在版本记录中查看。
- 已有新增正文后失败／取消：将拼接后的有效正文保留为可继续聊天的版本，标记本次中断并保留诊断；取消不自动触发下一次请求。判断依据是新增正文，不能只检测拼接全文是否非空。
- 客户端离线或刷新：从持久化的来源引用和本次增量恢复；仅前端断开时按现有后台执行机制继续，不额外请求模型。
- 来源有尚未落盘的已接收尾部时，先完成现有终止／检查点流程；无法确认的尾部不冒充已保存内容。停止请求尚未完成时不接受续写。
- 新请求不覆盖原回答状态。继续失败不损坏旧分支，也不自动重试产生额外请求和费用。

## 其他功能的一致性

| 入口                     | 预期行为                                                                                                           |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| 搜索／引用／复制         | 使用逻辑完整正文，搜索命中能定位到拼接版本                                                                         |
| 历史压缩                 | 将拼接版本视为一条回答；摘要覆盖范围绑定该分支，不借用旧分支的摘要                                                 |
| 分享／SSR                | 固化完整正文及分段思考，沿用模型名称不含供应商、思考默认折叠的规则；不公开私有输入回执                             |
| Markdown 导出            | 默认导出用户可见的完整回答和来源说明；显式过程导出再列实际「继续」请求及新增输出                                   |
| 备份／恢复／复制到新对话 | 保留或转为自包含内容引用，校验展开前后的正文哈希一致                                                               |
| MCP                      | 单独增加回答续写动作／参数，返回新版本和来源；现有用于定位后续对话的 continuation 令牌语义保持清楚，不混作正文续写 |
| MCP 分页                 | 返回完整逻辑回答的分页；`hasMore` 只表示还有内容可读，生成截断由独立结束原因表示                                   |
| 通知／用量               | 按本次独立执行处理，不为继承的前缀重新发通知或重复入账                                                             |

## 实施顺序

1. **数据与上下文**：定义提交动作、来源关系、正文解析器和独立生成记录；打通预算、输入回执及失败状态。先证明新请求的输入与后续普通聊天的输入符合本文示例。
2. **存储与流式**：实现前缀引用、增量检查点、分页、重连和生命周期；完成离线升级脚本及备份往返验证。不以完整复制所有前缀作为长期实现。
3. **界面与已有入口**：增加继续操作、新分支选择、分段思考和生成信息；统一搜索、摘要、分享、导出及复制读取逻辑。
4. **MCP 与验收**：在同一服务层开放显式续写，更新 help 和输入回执说明；通过本地回归与免费层相关测量，再经 PR 测试和维护窗口发布。

## 验收重点

- 一次及多次续写：旧版本不变，新版本为兄弟分支；正常后续只发送一条拼接回答，输入回执与实际模型输入一致。
- 来源分支已有后续消息、已存在摘要、切换模型或附件版本时，输入与新分支定位正确，不混入旧后续或草稿。
- 中断、长度结束、主动停止、只返回思考、零新增失败和增量后失败分别得到正确行为；网络断开但后台仍在生成时不能重复续写。
- 同请求重放、并发点击、源版本删除、切走后返回、DO 重启和重连均不重复启动或重复拼接。
- 在代码块、数学公式、空白边界、中文和代理对边界中断，拼接正文与原文加增量逐字相同；跨阶段工具信息和模型来源可追溯。
- 长前缀连续多次续写，测量数据库新增字节、行写入、解析 CPU、同步体积；确认没有逐次复制全文或逐 token 遍历来源链。只读页面可展开全文，流式通道只传新增量和必要元数据。
- 搜索、摘要、复制、导出、分享 SSR、MCP 分页、删除与离线备份往返得到同一正文；账本、通知和未知用量字段保持正确语义。
- Chromium／WebKit 验证流式渲染、滚动、分支切换与刷新恢复；生产验证只使用授权的测试对话，不以真实供应商请求替代确定性回归。
