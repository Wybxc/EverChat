# 回答完成通知：权限调研与实施计划

更新日期：2026-10-19。状态：A／B 阶段已实现，完成本地规则、原生运行时、生产 SW 和 Cloudflare 加密路径验证；C 阶段真实设备推送及完整投递资源验收进行中。macOS 后台／退出、iOS 锁屏／完全关闭 App 后的通知及点击定位已由用户确认，其他场景仍逐项验收。

## 目标与结论

在「设置 → 通用」增加「回答完成通知」，提供「始终发送／不发送／仅在无焦点或后台时发送」。设置自动保存，按当前设备的浏览器／PWA 安装实例生效。

网页能够发送系统通知，也能够通过 Web Push 在页面没有打开时接收通知；但通知授权、后台执行和推送订阅是不同的能力。**只增加 `Notification.requestPermission()` 和前端完成回调，不能可靠覆盖 iOS PWA 切到后台、锁屏或关闭后的提醒。**要完成这些场景，需要服务端在回答最终保存成功后投递 Web Push。[Push API](https://developer.mozilla.org/en-US/docs/Web/API/Push_API)、[页面生命周期](https://developer.chrome.com/docs/web-platform/page-lifecycle-api)

建议按「权限与页面通知 → 服务端完成投递 → 真机验收」实施。第一阶段可以独立交付，但必须明确仅在页面仍能接收完成状态时生效；整个功能完成以第二、三阶段覆盖后台场景为准。沿用现有 Cloudflare DO、Service Worker 和 Access，不增加常驻进程或逐 Token 通知。

## 1. 权限能够支持到什么程度

### 平台能力

| 环境                                      | 页面仍运行时的系统通知 | 挂起、锁屏或页面已关闭                                                | 前提与边界                                                               |
| ----------------------------------------- | ---------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 桌面 Chrome／Edge／Firefox 网页与 PWA     | 支持授权后的通知       | 需要 Web Push；能否在浏览器完全退出后送达取决于浏览器、后台设置和系统 | 不要求先安装 PWA；不能承诺进程被强制结束、离线时立即送达                 |
| macOS Safari 与独立网页 App               | 支持                   | 支持 Web Push；Apple 的系统集成允许 Safari 没有运行时接收             | 标准 Web Push 自 Safari 16.1／macOS Ventura 起提供；仍受系统通知设置影响 |
| iOS／iPadOS 普通浏览器标签页              | 不能按桌面网页能力承诺 | 不能作为本方案的系统推送入口                                          | 引导添加到主屏幕并从独立 App 打开；运行时继续检测能力                    |
| iOS／iPadOS 主屏幕 PWA，16.4 起           | 支持授权后的持久通知   | 通过 Web Push 接收，不依赖聊天页面继续执行                            | 必须由直接用户操作申请权限；通知可进入锁屏、通知中心，并受专注模式控制   |
| 内嵌浏览器、WebView、隐私模式、受管理设备 | 逐环境检测             | 不保证                                                                | API、存储或权限可能不可用，提供清晰状态，不以浏览器名称推断成功          |

Apple 平台依据：[iOS／iPadOS Web Push](https://webkit.org/blog/13878/)、[macOS Web Push 与系统后台进程](https://webkit.org/blog/12945/meet-web-push/)。其他浏览器以 [Push API 的标准能力](https://developer.mozilla.org/en-US/docs/Web/API/Push_API)和实际能力检测为准；以上是支持边界，不是真机验收结果。PWA 安装本身不会授予通知权限或永久后台运行权限。

### 可以申请、检测和执行

- 在 HTTPS 安全上下文中，通过明确的按钮操作申请通知权限；本地开发需使用浏览器认可的安全上下文。权限属于当前网站来源及浏览器／安装实例，不是给某个模型或供应商单独授权。[申请通知权限](https://developer.mozilla.org/en-US/docs/Web/API/Notification/requestPermission_static)
- 检测 `Notification.permission` 的 `default / granted / denied`，另行检查 Service Worker、`showNotification`、`PushManager` 和实际订阅结果。`granted` 不能代替「推送已配置」。
- 统一优先使用 `ServiceWorkerRegistration.showNotification()`。移动端不以 `new Notification()` 作为实现基础；MDN 明确指出多数移动浏览器的构造器会抛出异常。[Notifications API](https://developer.mozilla.org/en-US/docs/Web/API/Notifications_API)
- 从页面读取 `document.visibilityState` 和 `document.hasFocus()`；从同一 SW 管理的窗口汇总可见／焦点状态，用于应用自己的提醒策略。[页面状态判断](https://developer.chrome.com/docs/web-platform/page-lifecycle-api)
- 用户点击通知后，关闭该通知，聚焦已有窗口或打开同源对话 URL，再交给现有 SPA 路由恢复目标分支。[持久通知及点击事件](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerRegistration/showNotification)

### 无法通过网页权限保证

- 不能绕过用户拒绝、系统关闭通知、专注／勿扰模式、网络不可达或推送服务限制；也不能保证响铃、震动、横幅样式、显示时长和立即送达。
- 无法得知用户是否真正看到了通知；`showNotification()` 成功或推送网关接受，只能记录为已提交，不能标记为用户已读。
- 无法在权限被拒后自行改回允许；需要用户到浏览器或系统设置调整。不能在每次回答结束时反复请求权限。
- 页面失去焦点不等于用户一定没在看，浏览器地址栏、开发工具、分屏都会影响判断。网页也不能读取用户正在操作的其他 App 或系统专注模式的内部状态。
- SW 不是常驻后台进程，页面的 WebSocket、定时器和 fetch 回调在冻结后也不能保证执行。不要用 SW 长连接、音频保活或不断轮询来模拟后台通知。[生命周期限制](https://developer.chrome.com/docs/web-platform/page-lifecycle-api)

## 2. 三种模式的产品语义

| 选项                   | 行为                                                                                               |
| ---------------------- | -------------------------------------------------------------------------------------------------- |
| 始终发送               | 当前实例已授权且具备投递能力时，每条模型回答成功完成后提交一次系统通知，包括页面正在前台并有焦点时 |
| 不发送                 | 不再发起完成通知；停用本实例的服务端投递，尽力取消尚未发出的待投递项。已交给系统的通知可能无法撤回 |
| 仅在无焦点或后台时发送 | 同一账号所有设备都没有可见且有焦点的 EverChat 窗口时才提醒；页面关闭后的提醒需要 Web Push          |

建议默认选「仅在无焦点或后台时发送」，**首次打开网站不弹系统权限申请**。未授权时保留这个偏好，显示「未授权」及「启用系统通知」按钮；只有用户点击按钮才申请权限。它是建议默认值，实施时无需引入首启引导弹窗。

页面在线判断为 `document.visibilityState !== 'visible' || !document.hasFocus()`，同账号多设备、多窗口需要汇总后再决定。焦点指页面／窗口焦点，不是消息输入框焦点；打开设置、搜索弹窗或阅读另一段内容不能被误判为失焦。同一账号任一 EverChat 窗口有焦点时抑制所有设备的条件通知，即使该窗口正在查看其他对话；若未来要按「是否正在查看这条回答」提醒，应作为另一种明确语义。

模式、系统权限和订阅仍按浏览器／PWA 安装实例保存；条件通知的前台判断由服务端在同一账号内协调。电脑页面有焦点时也抑制手机的条件通知；未启用、拒绝或关闭电脑通知，不影响电脑参与焦点确认。Safari 标签页、独立 PWA 和其他浏览器仍各有独立的存储、权限及订阅，不合并物理设备身份，也不自动授予或开启通知。“始终发送”的实例不受其他设备焦点影响。

### 什么算一次回答完成

- 只对由模型生成、最终持久化状态进入 `completed` 的普通回答触发，包括重新生成产生的新版本；不在供应商流刚结束、正文还没有保存时触发。
- 搜索／Fetch／模型续接的每一轮不分别通知；整条公开回答完成时通知一次。标题生成、上下文摘要、能力测试、用户手动编辑、导入／复制的历史回答不触发。
- 失败和用户取消不以「回答完成」发送成功通知；保留现有错误展示。以后如需失败提醒，单独定义文案和策略。
- 首次读取历史、刷新、分支切换和备份恢复不补发历史通知。实时生成期间短暂断线后恢复，只有能确认是新完成且仍在有效投递期的任务可以提醒。
- 通知采用泛化文案「EverChat」「回答已完成」，不默认暴露提问、回答、思考或对话标题。携带跳转所需的对话 ID、回答 ID，以及稳定完成标识，不携带 API 密钥和 Access 凭据。

## 4. 推荐架构

### A. 页面通知与权限闭环

新增 `src/platform/notifications` 管理浏览器能力、授权、SW 交互和本地偏好；新增 `src/features/notifications` 管理回答完成规则及设置 UI，由 App 装配。业务规则不塞入 Markdown 渲染器、每条消息组件或 PWA 更新控制器。

1. 设置自动保存偏好，但权限与订阅状态始终来自浏览器实际状态。用「未授权／已拒绝／页面通知可用／后台推送已就绪／当前环境不支持」区分能力，不把一个开关显示为全部已启用。
2. 明确按钮直接调用权限申请，不在异步加载之后丢失用户手势。提前准备 SW 注册；生产 SW 尚未就绪时给出可重试状态，不无限等待 `serviceWorker.ready`。本地开发无生产 SW 时不得伪报后台推送可用。
3. 对可信的新终态提交通知请求，交给根 SW 统一检查当前模式、多窗口焦点和完成标识。消息协议独立命名并校验来源及字段，与现有 `everchat:pwa` 更新命令隔离。
4. 使用回答 ID 构成稳定完成标识，例如 `conversationId:assistantMessageId:completed`；工具轮次切换 `runId` 不改变它。通过共享 IndexedDB 原子认领与短期去重记录协调窗口，`tag` 只辅助替换，不能单独保证不重复响铃。
5. SW 在显示之前复核权限、偏好版本及退出状态。只为同一身份且仍有效的任务显示通知；显示失败不影响回答，也不触发供应商重试。
6. 第一阶段保证被在线实例观察到的完成状态；当前对话以外的生成、页面挂起或关闭后的覆盖由 B 阶段完成。不通过为每个对话另开 WebSocket 或加快全库轮询扩大覆盖。

同一浏览器存储分区内尽量做到每次完成只提交一次；IndexedDB 与系统通知之间不存在原子事务，崩溃窗口下不能承诺严格的 exactly-once。记录「已提交／失败」，不伪称「已送达／已读」。

### B. 服务端 Web Push：完整后台能力

1. 用户启用并授权后，通过现有根 SW 的 `pushManager.subscribe({ userVisibleOnly: true, applicationServerKey })` 获取订阅。VAPID 公钥交给客户端，私钥使用 Worker Secret；不把模型供应商密钥复用于推送。
2. 增加受现有 Access 与同源校验保护的订阅登记、模式更新和解绑 API。Library 保存当前安装标识、归属身份、模式及版本、启用时间、订阅端点与公钥材料。仅投递启用之后的新完成，避免刚授权就收到旧任务提醒。沿用当前单空间结构，不顺带改造为多租户，但仍校验订阅归属，不能仅信任客户端传入的身份。
3. 回答最终成功保存时，在所属 Conversation DO 的同一事务登记小型待投递项，包含完成 ID、回答 ID、完成时间和期限；事务提交后由投递模块交给 Library 获取目标订阅并分发。工具任务从运行变为最终成功的其他入口也必须复用这一规则。
4. 仅保留有期限、可幂等的投递意图及最小重试信息，成功或过期后清理；它用于恢复未完成的外部副作用，不承担重建聊天历史的职责。不恢复已删除的同步事件日志，不保存全文、SSE、Token 或每次状态变化。
5. 初始建议 TTL 为完成后 1 小时；在这个窗口内网络故障可有限退避，网关返回过期订阅则删除，认证错误停止盲目重试。复用 DO 已有 Alarm 调度并限制每次分发批量，不为每次完成创建 Workflow、Cron 或常驻轮询。
6. 采用经过验证、可运行于 Workers／Web Crypto 的标准 Web Push 实现。先测 VAPID 签名、负载加密、真实 Apple／其他浏览器端点和 CPU，确认后选库；不根据 Node 示例直接假定边缘兼容，也不自行发明推送协议。
7. 已登记 Push 的实例由服务端统一负责该次完成的投递，页面不再为同一实例并行本地通知；未启用 Push 的实例沿用 A 的本地路径。切换投递方式时共享完成标识与模式版本，避免两条链路各发一次。
8. SW 收到推送后直接用负载里的泛化文案显示通知，不先请求 `/api` 获取回答。Access 会话过期或后台请求被重定向不应阻断通知显示；点击后再进入正常鉴权。退出时先解绑当前订阅，离线退出至少本地取消订阅并使旧身份无效，随后核对已知绑定；已进入推送网络的通知仍可能到达。

订阅端点属于敏感投递地址，不输出完整端点或密钥材料到日志。登记时限制为受支持浏览器的 HTTPS 推送服务，服务端不跟随任意重定向或请求内网地址；发送日志只保留完成 ID、匿名安装标识、结果类别和时延。[订阅端点与后台投递](https://developer.mozilla.org/en-US/docs/Web/API/Push_API)

### 「仅在无焦点或后台时」的远程判断

这项不能简单地在 `push` 回调中写成「发现前台就直接 return」。WebKit 要求可见推送；反复收到消息却不显示，可能导致订阅被撤销。[WebKit 对可见通知的要求](https://webkit.org/blog/12945/meet-web-push/)

推荐在**发送 Push 之前**决定是否应发：

- 已登录页面建立休眠 WebSocket 控制通道，不依赖该页面启用通知。未登记订阅的页面只保留连接附件中的身份和会话期限，不新增持久化设备、焦点历史或周期租约。
- 以同一账号全部有效连接汇总状态；可见且有焦点才是前台。单个后台标签页不能覆盖另一个前台窗口；不同账号之间不发送或接受焦点确认。
- 每个条件投递通过已有连接向同账号窗口请求一次焦点确认，等待 1 秒后决定是否抑制；不延迟回答终态保存或界面显示。没有有效连接时正常投递；通道不依赖当前对话的消息订阅。仅本地通知的实例也先经过同一账号判断，再由目标实例的 SW 复核。
- 明确确认前台时不投递；明确在后台或关闭时投递。状态失联、过期且没有收到确认时按后台处理，优先避免漏提醒，并标记这是产品取舍。确认通道、等待期限和租约时长在实施前的竞态验证中确定。
- Push 一旦发出，就按平台要求显示。完成后用户恰好切回前台，或状态汇报因网络延迟迟到，仍可能看到通知；该模式是尽力匹配，不能承诺系统级瞬时焦点精度。

重复投递也不能在 `push` 回调里直接沿用 A 阶段「已显示就返回」的逻辑；应在发送端去重，接收端使用同一 `tag` 替换并设置 `renotify: false`，同时满足可见通知要求。平台是否再次响铃仍不能由应用绝对保证。

较新的 WebKit 还提供 Declarative Web Push，可以在 SW 不可用时由浏览器描述并显示通知；它仍不是静默后台执行通道。现有 EverChat 已有 SW，首期使用跨浏览器标准路径，后续再按能力评估声明式增强，不将其作为 iOS 16.4 起支持的前提。[Declarative Web Push](https://webkit.org/blog/16535/meet-declarative-web-push/)

## 5. 通知点击、设置与退出

- 通知点击复用 `/c/:conversationId?branch=:assistantMessageId`，先寻找同实例现有窗口；通过带版本和目标 ID 的消息交给 App 做 SPA 导航，再聚焦。不要直接导航刷新一个有草稿的窗口。没有窗口时才打开同源 URL。
- 初次载入、Access 重新登录与离线恢复都保留目标分支。对话已删除、目标版本不存在或权限不再允许时，进入正常的不可用状态，不自动重建或暴露旧正文。
- 「发送测试通知」只验证当前实例的授权与显示链路，不能宣称验证了锁屏远程推送。B 阶段提供可区分的真实推送验收步骤。
- 选择「不发送」自动保存并向服务端确认；离线时明确「停用待同步」，本地路径立即停止。浏览器中本就保存的通知权限无法被应用设置撤销，后续重新开启不必伪造一次新授权。
- 退出清理、切换身份、SW 更新和修复注册均核对订阅归属与当前登记状态；不能把旧身份的通知状态随对话备份导出／导入。新增持久结构如需历史维护，仅提供[离线运维迁移](../operations/offline-storage-migration.md)，不增加请求时数据搬运或回填。

## 6. Cloudflare 免费层与费用

页面通知不需要每次新增服务端投递；Web Push 需要每条完成向每个启用实例发送一次加密 HTTPS 请求，并产生少量 DO 读写、RPC／Alarm 和计算用量。Apple 的标准 Web Push 不要求加入 Apple Developer Program；方案也不依赖付费通知 SaaS，但这不等于 Cloudflare 资源零消耗。[Apple Web Push](https://webkit.org/blog/13878/)

调研时 Workers Free 为每天 100,000 次请求、普通 Worker 每次 10ms CPU；DO Free 为每天 100,000 次请求、13,000 GB-s，SQL 每天 500 万行读、10 万行写及 5 GB 总存储。沿用[免费层资源政策](../architecture/free-tier-resource-policy.md)，实施时重新核对账户和平台限制。[Workers 定价](https://developers.cloudflare.com/workers/platform/pricing/)、[DO 定价](https://developers.cloudflare.com/durable-objects/platform/pricing/)

资源增长应与「完成回答数 × 启用订阅数」相关，与输出 Token 数和原始流大小无关。采用有索引的订阅读取、小负载、批量投递、终态单次登记、到期清理；焦点租约优先留在协调模块内存，重启视为未知，不持久化焦点变化历史。不得借通知重建高频同步日志或给空闲实例增加持续轮询。

实际 Cloudflare CPU、发送成功率和最大分发批量必须测量后记录，不能以本地 Web Crypto 耗时证明免费层可用，也不新增用户此前拒绝的应用内每日配额或计费限制。

### 并发焦点确认与原生 WebSocket 修复

后续核对复现了三个焦点竞态：同一窗口同时确认多个完成时，只保留最后一个确认；旧回包或重复后台回包可以覆盖已经确认的前台状态；超过 1 秒决定期限的前台回包仍能取消投递。三个新增 SQLite 单测在修复前均失败。

### 2026-10-19：跨设备条件通知修正

用户反馈电脑页面活跃时，手机仍收到回答完成通知。原实现按订阅实例决定是否在前台，电脑的确认只会结束电脑自己的投递；手机关闭时没有本机连接，因此仍被投递。这是原先按设备定义的策略与使用预期不符。

条件模式现改为同账号任一页面可见且有焦点时抑制投递。焦点控制通道独立于系统通知权限：未启用或关闭通知的页面也可参与，不申请权限、不创建推送订阅，也不为仅在线页面新增持久化设备。服务端验证 Access 身份和会话期限，确认回包只结束同账号、当前随机尝试且未过期的条件投递；始终发送不受影响。退出会停止控制通道，跨账号、过期会话和迟到回包不能取消投递。沿用现有表和休眠连接，无数据迁移。
